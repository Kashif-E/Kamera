# Changelog

All notable changes to the Kamera project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.0] - Unreleased

### Removed (breaking)
- **No Intel iOS simulator artifacts**: the `iosX64` target is gone from every module, so 2.0 publishes klibs for `iosArm64` (devices) and `iosSimulatorArm64` (Apple-silicon simulators) only. Apps that still build for an x86_64 simulator must stay on 1.x or move their simulator builds to Apple silicon.
- **The core no longer supplies `androidx.camera:camera-extensions`** on Android, and no longer puts `androidx.activity:activity-compose` on consumers' compile classpath. Declare them if you use them directly.
- **`androidx.startup:startup-runtime` is gone from the core**, with CameraK's unused `AppContextInitializer` and its manifest provider. Apps that used androidx.startup only through CameraK must declare it.
- **ZXing is no longer exported by the core**: Android apps that used `com.google.zxing:core` through CameraK must declare it. `qr_scanner_plugin` no longer brings `com.google.zxing:javase` to desktop apps.
- **`kotlinx-atomicfu` is no longer exported** on the core's JVM and Android API.
- **Only the release Android variant is published**; consumers' debug builds resolve the release AAR through variant matching.
- **iOS `MemoryManager` and `BurstCaptureManager` are removed, with no deprecation release before them**: the public object `com.kashif.cameraK.utils.MemoryManager` (`initialize`, `updateMemoryStatus`, `clearBufferPools`, `getBuffer`, `recycleBuffer`, `getOptimalImageQuality`, `isUnderMemoryPressure`) and the public class `com.kashif.cameraK.capture.BurstCaptureManager`. 1.x never deprecated them, so code that calls them stops compiling on 2.0 without a warning first. Nothing in CameraK used them; `MemoryManager.initialize` added a memory-warning observer on every `viewDidLoad` that was never removed, and `BurstCaptureManager` accepted captures and never ran them. (The Android `MemoryManager` is deprecated, not removed; see Deprecated.)
- **Kermit is no longer exported**: the core declared `co.touchlab:kermit` as an `api` dependency that nothing in CameraK imported (CameraK logs through `CameraKLogger`), which pinned every app's Kermit version. Apps that use Kermit declare it.
- **`video_recorder_plugin` is no longer published**: recording is part of the core. `VideoRecorderPlugin`, `rememberVideoRecorderPlugin` and the plugin's `startRecording(outputDirectory)`, `stopRecording()`, `pauseRecording()`, `resumeRecording()`, `recordingEvents`, `isRecording`, `isPaused` and `recordingDurationMs` are removed with no deprecation release. Call the holder's recording commands (see Added), read `CameraKStateHolder.recordingState`, and collect `CameraKEvent.RecordingEnded` from `events`; set the output directory in `VideoConfiguration.outputDirectory`.
- **`CameraKStateHolder`'s 1.x recording calls are replaced**: the deprecated `startRecording(configuration)`, `stopRecording()`, `pauseRecording()` and `resumeRecording()`, which returned `Unit` and reported only through events, are gone. The suspend commands of the same names return their outcome: `startRecording(config)` a `CameraKResult<RecordingState.Recording>`, `stopRecording()` a `CameraKResult<RecordedVideo>`, `pauseRecording()` and `resumeRecording()` a `CameraKResult<Unit>`. A call site that ignored the result must now call them from a coroutine.

### Changed (breaking)
- **The core no longer exports Coil or Ktor** (was `api` on `io.coil-kt.coil3:coil-compose:3.5.0` and `io.coil-kt.coil3:coil-network-ktor3:3.5.0`, which brought the Ktor 3.1 client without an engine and registered a second Coil network fetcher). Nothing in the core used them. `image_saver_plugin`, whose `rememberImageSaverPlugin(context = ...)` takes a `coil3.PlatformContext`, now declares `io.coil-kt.coil3:coil-core` itself (`api`) and `coil-compose-core`. Apps that used Coil's `AsyncImage`, its network loading or Ktor through CameraK must declare `io.coil-kt.coil3:coil-compose`, a `coil-network-*` artifact and Ktor themselves. On iOS, ImageSaverPlugin's read failures are `kotlinx.io.IOException`, the type Ktor's `IOException` already aliased.
- **Desktop apps add their own bytedeco natives** (was `org.bytedeco:javacv-platform` in the core, OCR and analyzer plugins). The libraries now depend only on the Java bindings they import: the core on `org.bytedeco:javacv:1.5.12` (without its transitive bindings), `javacpp:1.5.12`, `ffmpeg:7.1.1-1.5.12` and `videoinput:0.200-1.5.9`; `ocr_plugin` adds `tesseract:5.5.1-1.5.12` and `leptonica:1.85.0-1.5.12`. Measured over the external artifacts on each library's `desktopRuntimeClasspath` (before at 7557510, after at this release): the core's falls from 201 jars and 735.9 MB to 47 jars and 26.1 MB, `analyzer_plugin`'s the same, and `ocr_plugin`'s to 49 jars and 26.3 MB; the three together fall from 2,207.8 MB to 78.6 MB. The bytedeco share of each falls from 708.5 MB to 1.2 MB (1.5 MB for OCR). An app then adds the natives for each platform it ships, for example 24.4 MB for macOS arm64 with OCR (FFmpeg 19.4 MB, Leptonica 3.4 MB, Tesseract 1.6 MB, JavaCPP 0.04 MB). Apps must add the natives for the platforms they ship, either classifier jars such as `org.bytedeco:ffmpeg:7.1.1-1.5.12:macosx-arm64` (plus `javacpp`, Windows `videoinput`, and for OCR `tesseract` and `leptonica`) or the `-platform` artifacts narrowed with the `org.bytedeco.gradle-javacpp-platform` plugin; see the README's Desktop setup. Without natives the camera does not open: a `CameraKStateHolder` ends the start in `CameraKState.Error(CameraKError.NativeLibraryMissing)`, which names the bytedeco platform and keeps JavaCV's failure (`NoClassDefFoundError`, "Could not initialize class org.bytedeco.ffmpeg.global.avutil") as its cause, and the OCR plugin's calls throw `UnsatisfiedLinkError` the first time and `NoClassDefFoundError` after that. OpenCV, OpenBLAS, librealsense, libfreenect, FlyCapture, libdc1394 and ARToolKitPlus no longer arrive through CameraK; apps that used them transitively must declare them.
- **`analyzer_plugin` no longer depends on ML Kit text recognition, JavaCV or Tesseract**, none of which it used. Android apps that relied on ML Kit text recognition arriving through it must declare `com.google.mlkit:text-recognition` themselves, and drop the ML Kit data-collection disclosure if nothing else uses it.
- **Gradle group is `io.github.kashif-mehmood-km`**, the published groupId, for every module (was `com.kashif.*`). Kotlin/Native klib unique names change with it, which matters only to libraries that compiled against a 1.x klib. An `includeBuild` of this repository still does not substitute the published coordinates on its own, because Gradle matches included projects by group and project name and the project names (`cameraK`, `ImageSaverPlugin`, ...) differ from the artifact ids (`camerak`, `image_saver_plugin`, ...); declare a `dependencySubstitution` for each artifact you include.
- **Android minSdk is 23** (was 21) for every module. 1.x already required 23 in practice: CameraX 1.5, Compose's Android artifacts, activity 1.13 and core-ktx 1.18 all declare minSdk 23, so an app at 21 or 22 failed its manifest merge. The build now checks that the declared minSdk equals the highest minSdk among the dependencies each library ships, and each library's unit tests merge their manifest at 23 and run their Robolectric tests at 23 as well as 35.
- **Built on Compose Multiplatform 1.11.1 and Coil 3.5.0** (were 1.10.3 and 3.4.0). The core exports Compose, and `image_saver_plugin` Coil, as `api`, so apps resolve at least these versions; an app pinned to Compose Multiplatform 1.10 must upgrade with CameraK 2.0.
- **Captures are app-private by default**: `CameraConfiguration.directory` defaults to `Directory.DOCUMENTS` on every platform (was `PICTURES`). On Android, DOCUMENTS photos and default-location videos move from `getExternalFilesDir(null)/CameraK` to internal `filesDir/CameraK`; on iOS default captures move from the Photos library to `Documents/CameraK`. Existing files are not moved. Apps that relied on captures appearing in the gallery set `directory = PICTURES` (or `DCIM`) or attach `ImageSaverPlugin` with auto-save.
- **Android gallery captures return a `content://` URI**: PICTURES and DCIM photos are inserted through MediaStore and return the new `ImageCaptureResult.SuccessWithUri` instead of `SuccessWithFile`, so an exhaustive `when` needs a branch for it. From API 29 no storage permission is needed; the manifest declares `WRITE_EXTERNAL_STORAGE` with `maxSdkVersion="28"`.
- **Android capture file names** change from `<prefix>_yyyyMMdd_HHmmss.<ext>` to `<prefix>_<epoch ms>_<8 hex>.<ext>`, for photos, videos, gallery entries and ImageSaverPlugin's default names, so two captures in one second no longer collide. A capture whose file cannot be created returns `ImageCaptureResult.Error` instead of throwing.
- **Android `ImageFormat.PNG` captures are JPEG**, named `.jpg` and registered as `image/jpeg`, because CameraX's file output always encodes JPEG; configuring PNG logs a warning. ImageSaverPlugin on Android labels saved images by their actual bytes.
- **The core's manifest merges `android.permission.CAMERA`** and `uses-feature` entries for `android.hardware.camera.any`, `camera`, `camera.autofocus` and `camera.flash`, all `required="false"`. Google Play therefore no longer infers a required back camera with autofocus from CAMERA; an app that needs one declares the feature `required="true"` itself (the merger ORs `required`).
- **Android analyzer frames are read-only**: the `ImageProxy.planes` that analyzers registered with `registerImageAnalyzer` receive are read-only views, one per analyzer, in the source buffer's byte order. Writing to a plane buffer throws `ReadOnlyBufferException`.
- **Android `QualityPrioritization.NONE` always captures with `CAPTURE_MODE_MAXIMIZE_QUALITY`**, the same as `QUALITY`. Before, it dropped to `MINIMIZE_LATENCY` whenever device-wide RAM use went above 80%.
- **External cameras are listed apart**: `LensInfo` gains `isExternal: Boolean = false` (source compatible; the data class's binary signature changes). `CameraCapabilities.lenses(lens)` and `availableDeviceTypes(lens)` leave out external cameras, which the new `CameraCapabilities.externalLenses` lists. On Android, `LENS_FACING_EXTERNAL` cameras report `lens = BACK` with `isExternal = true`.
- **`LensInfo` is a plain class**, not a data class: it keeps its eight constructor parameters and compares, hashes and prints by value, but `copy()` and `component1()` to `component8()` are gone. **`CameraCapabilities` compares by value** (before, by identity): two capabilities are equal when every lens and every reported mode and format is equal.
- **`ImageFormat.HEIC`** (`heic`, `image/heic`) is a new entry, so an exhaustive `when` over `ImageFormat` needs a branch for it. No platform writes HEIC yet: a capture configured as HEIC returns `ImageCaptureResult.Error` with an `UnsupportedOperationException` ("HEIC capture is not supported yet"), logs one warning, and writes no file or gallery entry.
- **Android lens device types are relative to the main lens**: each lens of a facing is compared with that facing's main lens, the largest readable sensor among the single-focal lenses between 20 mm and 70 mm (35 mm equivalent; a tie goes to the shorter lens). A lens at 1.6x the main lens's equivalent focal length or more is `TELEPHOTO`, one at 0.75x or less `ULTRA_WIDE`. Before, only absolute thresholds counted (20 mm or less ultra-wide, 70 mm or more telephoto), so a 2x telephoto beside a 24 mm main lens was reported as `WIDE_ANGLE`; `CameraDeviceType.TELEPHOTO` can now select a lens it did not select in 1.x. A facing with no main lens, and a lens whose sensor width is unreadable, still use the absolute thresholds.
- **`CameraConfiguration` gains five fields** with defaults that keep 1.x behaviour: `cameraId: String? = null`, `outputDirectory: String? = null`, `frameAnalysis: Boolean = false`, `analysisResolution: Resolution? = null` and `analysisFormat: FrameFormat = FrameFormat.YUV_420` (source compatible; the data class's binary signature changes). The 2.0 engines read them; the 1.x controllers ignore them.
- **`VideoConfiguration` validates its limits, and its limits are nullable**: `maxDurationMs: Long` becomes `maxDuration: Duration?` and `maxFileSizeBytes` (new in 2.0) is a `Long?`; `null` means unlimited for both (was `0`). A negative `maxDuration` or `maxFileSizeBytes` throws `IllegalArgumentException`; before, a negative value meant unlimited. `filePrefix` must be 1 to 64 characters from `A-Z a-z 0-9 . _ -` and not `.` or `..`, or the constructor throws. `enableAudio` defaults to `false` (was `true`): a recording asks for the microphone only when the app sets it. On Android the CameraX Recorder enforces both limits, and a positive `maxDuration` under 1 ms is applied as 1 ms, since CameraX reads 0 as unlimited.
- **Desktop controller lifecycle**: `CameraController.cleanup()` is final; `startSession()` after `cleanup()` is logged and ignored, so create a new controller. A new controller's session waits for an older controller's grab loop on the same camera to release it before opening the camera.
- **Desktop capture locations**: photos land in `~/Pictures/CameraK` (PICTURES, DCIM) or `~/Documents/CameraK` (DOCUMENTS) instead of `java.io.tmpdir`. Videos without an `outputDirectory` go to `~/Movies/CameraK` (macOS) or `~/Videos/CameraK` (Linux, Windows), not a working-directory `captured_videos` folder. A folder the controller creates is `rwx------` and each photo `rw-------` where POSIX permissions exist. A throwing image-capture listener no longer turns a capture into `Error`: the photo is kept, the result is `SuccessWithFile`, and the listener's exception is logged. With no listener registered, the file is not read back.
- **Desktop recording**: `VideoConfiguration.enableAudio = true` records video only and logs a warning; the file has no audio track. A camera faster than 30 fps is recorded at 30 fps.
- **Desktop analyzer frames are owned JPEG bytes**: `AnalyzerPlugin`/`startAnalyzer` emits a JPEG per frame, as on Android and iOS, instead of the raster's raw BGR backing array.
- **Desktop preview letterboxes to the camera frame's aspect ratio**, not the configured `CameraConfiguration` ratio (which is used only until the first frame). The overlay's box is that letterboxed frame, so overlay coordinates change.
- **Desktop default camera on Linux** is the lowest-numbered V4L2 node (sorted numerically) that udev records as capture-capable, or without a udev record the lowest-numbered node with sysfs index 0. A machine whose first node by name was `video10`, a metadata node or a non-capture node now opens a different device.
- **Desktop ImageSaverPlugin names and folders**: with no `customFolderName`, images go to `~/Pictures/CameraK` (PICTURES, DCIM) or `~/Documents/CameraK` (DOCUMENTS), as on Android and as CameraK's desktop captures do, instead of straight into `~/Pictures` or `~/Documents`. `imageName` and `customFolderName` must each be 1-64 characters from `[A-Za-z0-9._-]` and not `.` or `..`; any other name fails the save with an `IllegalArgumentException` (`ImageSaveResult.Failed`; `saveImage` returns null). The auto-save prefix may be at most 50 such characters, and `JVMImageSaverPlugin` (so also `rememberImageSaverPlugin` on desktop) throws `IllegalArgumentException` when it is created with any other prefix, instead of failing every auto-save. An output folder that is a symbolic link fails with an `IOException`, wherever the link points, including to a folder beside it in the same directory. A save never overwrites: a taken name gets a numeric suffix (`shot_1.jpg`), and unnamed saves are `image_<yyyyMMdd_HHmmss_SSS>`. Bytes already in the configured format are written unchanged, keeping EXIF; a format change converts once at JPEG quality 0.95 and flattens transparency onto white.
- **Desktop ImageSaverPlugin reads only its own folders**: `getByteArrayFrom` and `readBytes` read only files that resolve, after `..` and symbolic links, into the saver's own folder (`<directory>/<customFolderName or CameraK>`) or into `~/Pictures/CameraK` or `~/Documents/CameraK`, where desktop captures go. The user's other files in Pictures and Documents are refused, and a CameraK or custom folder that is itself a symbolic link, even one pointing at Pictures, Documents or a folder inside them, is not read. Any other path, and any read failure, throws an `IOException` whose message contains no path. `onImageSavedFailed` gets a reason with no path: the saver's own message, or `Image could not be saved (<exception type>)`. A throwing `onImageSaved` no longer turns a save into a failure.
- **ImageSaverPlugin auto-save calls `save()`** instead of `saveImage()`, so a subclass's `save()` override runs on auto-save, and a failed auto-save emits `CameraKEvent.PluginFailed`.
- **Desktop OCR language data**: Tesseract data is no longer searched for in the working directory or the repository tree. Set `OcrConfig(tessdataPath)`, package the pinned `eng.traineddata` at `com/kashif/ocrPlugin/tessdata/`, or set `TESSDATA_PREFIX`. `OCRProcessor(config)` throws `TessdataNotFoundException` or `IllegalStateException` at creation instead of logging and returning null from every scan, and `OcrPlugin.extractTextFromBitmap` on desktop with no tessdata throws inside the consumer's `coroutineScope.launch`, matching Android. `OCRProcessor()`, the `OcrPlugin` constructor, `extractTextFromBitmapImpl` and `startRecognition` gained an `OcrConfig` parameter with a default: source compatible, JVM signatures changed.
- **Live OCR reads at most `OcrConfig.maxFps` frames a second** (default 2) on Android and desktop, so `textFlow` and `TextRecognized` emit less often; raise `maxFps` for per-frame results. On desktop the hidden 200 ms throttle in `OCRProcessor` is gone and `OCRProcessor.scanImage` reads every frame it is given. iOS live OCR uses Vision's fast level and 420f frames; the public iOS class `VideoDataDelegate` gains a `maxFps` constructor parameter (klib ABI change).
- **QR scanning is gated at one decode per 200 ms** by default on Android, where every analysis frame was decoded; pass `QRScannerPlugin(scope, scanIntervalMs = ...)` to change it. `rememberQRScannerPlugin` gained a `scanIntervalMs` parameter (source compatible; the composable's binary signature changes).
- **`QRScannerPlugin.pauseScanning()` stops the platform scanner**, and the pause holds when the camera becomes ready again until `resumeScanning()` or `startScanning()`. Before, a new `Ready` silently undid a pause.
- **An exception thrown by the `onQrScanner` callback on Android propagates** out of `analyze()`, where CameraK's analyzer multiplexer logs and contains it, instead of being swallowed.
- **Plugin results reach `CameraKStateHolder.events` through one latest-wins forwarder**: a slow collector gets the newest `QRCodeScanned` or `TextRecognized` rather than every frame's.
- **iOS flash and torch follow the configuration**: the configured `FlashMode` reaches captures (before, `FlashMode.OFF` could still fire the flash) and the configured torch is applied whenever the session starts and after every lens or device-type switch. `CustomCameraController.torchMode` defaults to `OFF` (was `AUTO`).
- **iOS lens switch during a recording is refused**: switching lens or camera device type while recording is logged and reported to `onError`, instead of stopping the session and cutting the recording. A camera input the session refuses keeps the previous camera instead of leaving the session without one.
- **iOS session preset**: a portrait `targetResolution` (for example 1080x1920) selects the matching preset instead of the aspect-ratio preset, and a preset the session cannot take falls back to the next one down, ending at High, instead of crashing.
- **iOS outputs are attached on demand**: the metadata output is attached only while a metadata delegate is set, and the movie file output only for a recording. The first `startRecording` pays one session reconfiguration, and the microphone input is removed when the recording ends.
- **iOS image-capture listeners run for every `takePictureToFile` capture**, as on Android, and so does ImageSaverPlugin auto-save. An app that saves to `PICTURES` or `DCIM` and also uses auto-save gets two copies until a single owner persists each capture.
- **iOS allows three captures in flight**, as on Android; a capture started while another is processing runs instead of failing with "Capture in progress". `QUALITY` captures are sized with `maxPhotoDimensions` instead of the deprecated high-resolution flags.
- **iOS orientation**: `setTargetOrientation` sets the photo's orientation, as documented, and no longer rotates the preview. The preview follows the interface (window scene) orientation instead of the device orientation, so portrait-locked apps keep an upright preview.
- **iOS recording lifecycle**: `startRecording` suspends until AVFoundation has started recording and throws `IllegalStateException` while a recording is in progress (before, it returned the running recording's path). `pauseRecording` throws `UnsupportedOperationException` below iOS 18 (before, it silently kept recording) and `IllegalStateException` when the output does not confirm the pause.
- **iOS recording outcome and location**: a recording AVFoundation reports as not successfully finished returns `VideoCaptureResult.Error` (was `Success`). `DOCUMENTS` videos without an `outputDirectory` are written under `Documents/CameraK` instead of the temporary directory. A recording keeps 200 MB of disk free and stops at `VideoConfiguration.maxDuration` when it is set.
- **iOS Photos imports are bounded and keep the file on failure**: with `Directory.PICTURES` or `DCIM`, an import Photos does not finish within 60 s (for example while its permission prompt is unanswered) makes `takePictureToFile()` return `ImageCaptureResult.Error` and `stopRecording()` return `VideoCaptureResult.Error`; before, they waited forever. When an import fails or times out, the captured photo or video is kept at its temporary path (photos used to be deleted; a failed video import used to return `Success` with that path), and the error message names Photos' error domain and code, or the timeout.
- **iOS PNG captures and `saveImage` keep the original pixels and metadata**: PNG captures keep the sensor's pixel layout and carry the EXIF orientation as metadata, instead of being redrawn upright without an orientation tag. iOS `ImageSaverPlugin.saveImage()` stores the bytes it is given unchanged as the Photos asset (EXIF, GPS and orientation kept, no re-encode), instead of an upright, re-encoded copy without metadata; for data that is not an image, `onImageSavedFailed` gets "The data is not an image."
- **iOS `IOSImageSaverPlugin.getFilePathFromAsset()`** writes to `Library/Caches/CameraK/IMG_<uuid>.<real extension>` (heic, png, jpg, ...) instead of `tmp/IMG_<uuid>.jpg`, and returns null for data of a type with no known image extension. The caller owns the file and deletes it; iOS may purge Caches.
- **iOS errors carry the platform's `NSError`**: the constructors of `CustomCameraController.CameraException.ConfigurationError` and `CaptureError` gain an optional `cause`, and `DeviceNotAvailable` gains an optional `message` and `cause` (source compatible; the klib ABI changes). A camera AVFoundation refuses to open, for example when camera access is denied, is reported as `ConfigurationError` carrying the `NSError` instead of `DeviceNotAvailable`. Photo-capture and recording error messages say "domain code"; the description is in the cause.
- **iOS metadata callbacks run off the main thread**: a delegate passed to `CameraController.setMetadataObjectsDelegate` is called on CameraK's serial background queue `com.kashif.cameraK.metadata` instead of the main queue. The QR scanner plugin already hops to `Dispatchers.Main`, so its callback is unaffected.
- **`CameraKState` is the 2.0 lifecycle**, a closed `sealed interface`: `Idle`, `Starting`, `Ready`, `Interrupted(reason: InterruptionReason)`, `Error(error: CameraKError)` and `Closed` (was a sealed class of `Initializing`, `Ready(controller, uiState)` and `Error(exception, message, isRetryable)`). An exhaustive `when` needs the new branches. `Ready` carries no `uiState` (read `CameraKStateHolder.uiState`) and its `controller` is deprecated and throws over an engine with no 1.x controller, such as camerak-testing's `FakeCameraEngine`. `Error` carries the typed `CameraKError`, with the platform's cause, in place of `exception` and `message`; `isRetryable` is the error's. `Interrupted` means the platform holds the session and resumes it on its own (a call, multitasking, another app holding the camera).
- **`CameraKStateHolder` runs on the platform's camera engine** and owns its coroutine scope. `CameraKStateHolder(config, platformContext, plugins)` builds it over the platform engine; `start()`, `stop()`, `retry()`, `recheckPermission()`, `close()` and `suspend closeAndJoin()` drive it, and `cameraState` reaches `Ready` only once the platform reports the camera open. Before opening it asks the environment's permission checker and publishes `Error(Permission)` when the camera is not granted; the production constructor's checker reads the platform's status (Android's grant and recorded requests, AVFoundation and Photos on iOS, macOS's camera authorization on desktop, Granted on Linux and Windows), so a denied camera is `Error(Permission)` instead of a failed open. A start the platform does not answer within 10 s ends in `Error(Timeout(START))`, or in `Error(Permission(NotDetermined))` while the permission is still undetermined (a platform that prompts on open), a runtime failure stops the camera and ends the session in `Error`, and `close()` publishes `Closed`, detaches the plugins, then closes the engine, waiting at most 5 s for it. A 1.x command (`captureImage`, the recording calls) still running at `close()` is cancelled without a `CaptureFailed` or `RecordingFailed` event or a `lastError`.
- **`rememberCameraKState` builds its holder through `rememberCameraKStateHolder`**: the camera starts when the host lifecycle reaches STARTED and stops below it, the permission is re-checked on every resume, and the holder closes when it leaves the composition (was `initialize()` on first composition and `shutdown()` on dispose). `camerak` exports `org.jetbrains.androidx.lifecycle:lifecycle-runtime-compose` 2.9.6 (`api`), whose `LifecycleOwner` the new composable's signature names.
- **The 1.x `CameraController` is a facade over the platform engine** on every platform: each public constructor and builder builds an engine of its own, `startSession()` starts it, `stopSession()` stops it and `cleanup()` closes it. Captures, recordings, analyzers and the flash, torch and zoom setters keep their 1.x behaviour.
- **Android camera errors are typed**: CameraX camera states map to the session's state. A recoverable error is `Interrupted` (`IN_USE_BY_ANOTHER_CLIENT` for a camera in use or too many open cameras, `OTHER` otherwise) and becomes `Error(Hardware)` when CameraX has not recovered within 10 s; a stream-configuration error is `Unsupported(ASPECT_RATIO)`, or `VIDEO_QUALITY` when the bind included video; a disabled camera or Do Not Disturb is `CameraDisabled`; any other critical error is `Hardware` with CameraX's code and cause. `stopSession()` keeps the use cases bound, so the next start reopens without a rebind; `cleanup()` unbinds only CameraK's own use cases. The orientation sensor runs only while the session is started. `camerak-core` on Android depends on `androidx.tracing:tracing` 1.2.0 (runtime scope; CameraX 1.5.3 already brings it) and writes `CameraK.start` and `CameraK.firstFrame` trace sections.
- **iOS 16 is the minimum**: below iOS 16 the camera makes no session and every engine call returns `Unsupported(PLATFORM_VERSION)`, so the holder ends its start in `Error`. `QUALITY` captures are sized with `maxPhotoDimensions` only; the high-resolution-flag fallback is gone.
- **iOS `CameraController` is no longer a `UIViewController`**: it is a plain class, `startSession()` starts the camera with no view, and camerak's `CameraPreviewView` hosts the preview layer in a view of its own. Code that presented the controller, added its `view` or called `viewDidLoad`/`viewDidLayoutSubviews` must use `startSession()` and `CameraPreviewView` instead.
- **iOS session errors are typed and keep the `NSError`**: every `AVCaptureSessionInterruptionReason` maps to an `InterruptionReason` (anything unknown is `OTHER`); a media-services reset is `Interrupted(MEDIA_SERVICES_RESET)` and restarts the session, again after every restart that ran, while a reset before the restart ran, or a restart after which the session does not run within 10 s, ends in `Error(Hardware)`; a device used by another session is `CameraInUse`, a disconnected device `Disconnected`, an unauthorized app `Permission(CAMERA, PermanentlyDenied)`, a session that is not running `NotReady`, and any other error `Hardware` with its code. The `NSError` is each error's cause. Start and first-frame intervals are written as `os_signpost` intervals named `CameraK`.
- **Desktop camera errors are typed**: missing bytedeco natives are `NativeLibraryMissing` with the natives' platform name (for example `macosx-arm64`), a busy device (`EBUSY`) is `CameraInUse`, a camera macOS denies or restricts is `Permission`, and any other failure is `Hardware` with FFmpeg's code. When the camera will not open at CameraK's size and frame rate, the open is retried once at the camera's own mode. After the camera opens, a failed grab or no frame for 5 s is `Interrupted(OTHER)` while the engine reopens the camera with backoff, and `Error(Disconnected)` after 10 s. `startSession()` and `stopSession()` begin or end the session before they return, and a stop interrupts a grab the camera driver leaves sleeping. On macOS the camera authorization is read through JNA when the app ships `net.java.dev.jna:jna` (CameraK declares it compile-only, so no classpath changes); without it the status reads as not determined.
- **`CameraKStateHolder` commands are suspend functions that return the applied value**: `capture(): CameraKResult<CapturedImage>`, `setZoom(ratio): CameraKResult<ZoomState>`, `setFlashMode`, `setTorchMode`, `selectCamera(lens, deviceType)`, `selectCamera(id)` and `setTargetOrientation`, replacing the non-suspend `setZoom`, `setFlashMode`, `setTorchMode` and `setTargetOrientation` of the same names. Outside `Ready` a command returns `NotReady`, after `close()` `Closed`, and a thrown exception `Internal`. `setZoom` returns the ratio clamped into the camera's range, and while one zoom or orientation call is in flight a newer one replaces any pending call, whose callers get the newer call's result. A fourth capture in flight is `Busy(CAPTURE)`. Every successful capture also reaches `captures` (a `SharedFlow` buffered to 64), a cancelled caller's included; `zoom` and `capabilities` are the engine's flows. `close()` detaches the plugins, lets running commands finish for up to 2 s, then closes the engine.
- **`CameraKStateHolder.uiState` is derived from what the platform reports**: flash, torch, lens, device type and zoom follow the bound camera, so a command shows there only once the platform has applied it, and it no longer goes stale after `close()`. `CameraUIState` gains `pendingCaptures`, `cameraId` and `targetOrientation`; `cameraLens` is null before the first bind; `isCapturing` is `pendingCaptures > 0`; `lastError` is always null, because a command returns its failure. `updateUIState` writes nothing. `events` is buffered to 64, dropping the oldest.
- **`CameraKEvent` is an abstract class with an internal constructor** (was a sealed class), so CameraK can add events in a minor release: a `when` over an event needs an `else` branch, and apps cannot create events. **`CameraKEvent.PluginFailed` carries `pluginId: String` and `error: CameraKError`** (was a data class over `error: Throwable`): the plugin's `id` (by default its class's simple name), or `"pluginScope"` for a failure in a coroutine of the deprecated shared plugin scope, and the throwable as `CameraKError.Internal`'s `cause`. Its constructor is `@InternalCameraKApi`.
- **Engine hardware commands answer `NotReady` until the camera is open**: `setFlashMode`, `setTorchMode` and `setZoom` on every engine, the fake included, return `NotReady` in every state but Open (the desktop engine's `setFlashMode(OFF)` used to succeed before Open). `setTargetOrientation` is configuration: every engine accepts it in any state before `close()`, applies it at the next bind or capture, and returns `Closed` after. On every platform the 1.x `CameraController` keeps a flash, torch or zoom set before `startSession()` and applies it when the session opens.
- **Android flash, torch and zoom are read back from CameraX**: `hardware` follows the bound camera's torch and zoom state, and the flash is read from the bound `ImageCapture` after every set and bind. Flash `ON` or `AUTO` and torch `ON` on a camera without a flash unit, and torch `AUTO` on any camera, are `Unsupported`; `setZoom` clamps to the range CameraX reports, which can start below 1x, and a fixed-zoom camera refuses any other ratio with `Unsupported(ZOOM)`. Capabilities take a bound camera's flash support from `CameraInfo.hasFlashUnit` and list torch `OFF` and `ON` only. The configured or previously set torch and zoom are applied once the camera opens, where the first start used to lose them. The 1.x `toggleTorchMode()` cycles `OFF` and `ON`, and `setTorchMode(AUTO)` is logged and ignored (it turned the torch on). With `CameraConfiguration.frameAnalysis = true` the first bind includes the analysis, so a plugin that needs frames no longer causes a second bind at start. A display rotated while the camera is stopped is applied at the next start, which rebinds when the orientation category changed. `selectCamera` is written as a `CameraK.lensSwitch` trace section.
- **iOS flash, torch and zoom are read back from the device**: torch and zoom follow the device by key-value observing, and a torch that is on but dark (thermal shutoff) is reported `OFF`; the flash is the photo output's validated mode. `setZoom` clamps into the device's range before the device sees it, and the range ends at `maxAvailableVideoZoomFactor`, which the 1.x `getMaxZoom()` also returns (the same as before on any camera that is not a virtual depth camera). A fixed-zoom camera refuses any other ratio, and a torch mode the device does not offer is `Unsupported(TORCH)`, and a configuration lock the device refuses returns `Hardware`. Torch modes per lens come from the device. `CameraKStateHolder.deviceOrientation` follows the device between start and stop (face up, face down and unknown keep the last value). A lens or device-type switch the session refuses leaves the 1.x controller's lens unchanged. `selectCamera` is an `os_signpost` interval `CameraK.lensSwitch`, with a `CameraK.lensSwitch.failed` marker for a switch that fails.
- **Desktop cameras are enumerated and selectable**: every camera is listed without opening any, with `LensInfo.id` the `/dev/v4l/by-id` link name (else the node path) on Linux, the `AVCaptureDevice` `uniqueID` on macOS and the DirectShow name on Windows; `""` only for the one default entry offered when the list cannot be read. On Windows cameras open through FFmpeg's DirectShow input (was videoInput). `selectCamera(lens)` takes the first camera of that facing, external cameras included, else the first camera; `selectCamera(id)` opens that camera and returns at its first frame, an id not listed (or a camera gone at open) is `NoCamera`, and a camera that fails to open returns its error and reopens the previous one. The camera lock is per device, so two cameras can run at once. A `DesktopGrabberFactory` receives the selected camera's id on every open, and the grabber it returns is started as returned, so an FFmpeg grabber for a stream is no longer opened as an AVFoundation camera on macOS. Flash and torch `OFF` and zoom 1 succeed while open and any other value is `Unsupported`; the 1.x `getCameraCapabilities()` lists the enumerated cameras.

- **Android previews render through CameraX's `CameraXViewfinder`** (`androidx.camera:camera-compose`, at the CameraX version, now a dependency of camerak on Android), not a `PreviewView` in an `AndroidView`: both `CameraPreview(holder)` and the 1.x `CameraPreviewView`. The frame is fitted to the box (`ContentScale.Fit`, as 1.x's `FIT_CENTER`), and CameraX still picks the implementation mode per device. The overlay spans the preview's whole box, letterbox bars included, as it did over the `PreviewView`.
- **A plugin is attached with its own `CameraKPluginContext`**: each attachment gets a new context whose `scope` is a supervisor child of the holder's scope, cancelled right after `onDetach`. A throw from `onAttach`, `onDetach` or a coroutine in that scope, a `reportFailure`, or a frame registration through `context.frames` that comes back rejected sets that attachment's `failure` and emits one `CameraKEvent.PluginFailed` with the plugin's `id`; later failures of the same attachment are only logged, and the camera and the other plugins carry on. A 1.x plugin that implements only `onAttach(stateHolder)` keeps working: the default `onAttach(context)` calls it.
- **A holder created with a plugin that needs frames binds frame analysis at start**: `CameraKPlugin.needsFrames` defaults to true, and a plugin passed when the holder is created with it set turns on `CameraConfiguration.frameAnalysis` for the engine, so the first analyzer registration needs no rebind. A 1.x plugin that reads no frames gets an analysis use case bound until it overrides `needsFrames = false`; `ImageSaverPlugin` does.

### Fixed
- **A plugin that threw an `Error` broke the camera**: `onAttach` and `onDetach` caught only `Exception`, so a `NotImplementedError` (a `TODO()` body) or a `LinkageError` from a plugin ended the session and kept the later plugins from attaching, and from `onDetach` stopped the release before the camera closed. Any non-fatal throwable from a plugin is now logged and reported as `CameraKEvent.PluginFailed`, and the camera and the other plugins carry on. The holder's release always ends its scope, even when the engine's close throws.
- **POM licence said MIT**: every published POM declared the MIT licence while `LICENSE` and the README grant Apache 2.0, so licence scanners saw two contradictory licences. The POMs now declare The Apache License, Version 2.0, from one entry in `gradle.properties`, and the build fails if any POM disagrees with `LICENSE`. All releases, including 1.x, are Apache 2.0.
- **POM metadata**: `ocr_plugin` was published under the name `qrScannerPlugin`, and `qr_scanner_plugin` and `ocr_plugin` both described themselves as "Image Saver Plugin for CameraK". Version, group and the shared POM fields now live once in `gradle.properties`, with each module's name, artifact id and description in its own `gradle.properties`.
- **Desktop capture and recording raced the preview for the camera**: `takePictureToFile()` and the recording loop each called `grab()` and the shared frame converter from their own threads while the preview loop did the same. On Windows the grabber is unsynchronised, so this could crash the JVM; elsewhere a photo could be the preview's half-overwritten buffer, and each extra grab took a frame away from the preview (recording roughly halved the preview rate). One grab loop on its own thread now owns the grabber and converter. A capture saves a copy of that loop's next frame, and recording takes its frames from that loop instead of grabbing its own every 33 ms. If the encoder falls behind, the recording skips to the newest frame rather than queueing. If the camera stops while a recording runs (or was never started), the recording now ends and `stopRecording()` returns `VideoCaptureResult.Error` instead of waiting for frames and then reporting success, and a grabber that stops delivering frames ends the session with an error instead of spinning the grab thread.
- **Desktop freed native handles while they were still in use**: stopping the camera released the frame grabber while the grab loop could still be inside `grab()`, `stopSession()` followed by `cleanup()` released it twice, and stopping a recording stopped the encoder while a frame was still being encoded. Stopping desktop OCR freed the Tesseract handle while a scan could still be running in it. Each handle is now released by the coroutine that uses it, once, after its last call returns; `stopSession()`, `cleanup()` and `RecognitionHandle.stop()` return without waiting. `stopSession()` followed by `startSession()` on the same controller now waits for the previous grab loop to release the camera before opening it again, instead of running two loops on one grabber. A recorder whose `start()` fails is released, and a second `startRecording()` while recording now throws `IllegalStateException`, as on Android, instead of orphaning the first recorder.
- **Android ImageSaver ignored `Directory.DOCUMENTS` and `customFolderName`**: on API 29+ a `DOCUMENTS` save was inserted into `MediaStore.Images`, which accepts only `DCIM/` and `Pictures/`, so every such save failed. It now goes through `MediaStore.Files` and lands in `Documents/<customFolderName or CameraK>/`. Below API 29 the saver set no file path, so MediaStore put every image directly in `Pictures/` regardless of `directory` and `customFolderName`; it now writes to `<directory>/<customFolderName or CameraK>/` like newer versions. The file is created before the MediaStore row, taking the first free name, so neither an existing file nor a concurrent save with the same name is overwritten, and path separators in `imageName` are replaced with `_` so the file cannot land outside that folder.
- **`kotlinx-coroutines-test` shipped to consumers, breaking `Dispatchers.Main`** (#165): `cameraK` declared `kotlinx-coroutines-test` as an `api` dependency of `commonMain`, so it landed in the published POM at runtime scope and reached every app that depends on `camerak` — or on any plugin, since each one re-exports the core with `api`. That artifact registers a `TestMainDispatcherFactory` through `ServiceLoader`, which takes over `Dispatchers.Main`; an app that never calls `Dispatchers.setMain()` then dies with *"Dispatchers.Main was accessed when the platform dispatcher was absent and the test dispatcher was unset"*. Reported on Desktop/Windows, but the leak was on every target. The dependency is now test-only. Consumers who were unknowingly relying on it for their own tests must declare it themselves; the `configurations.all { exclude(...) }` workaround is no longer needed.
- **iOS ImageSaver hung reading an asset and blocked the main thread while saving**: `getByteArrayFrom()` (and `getFilePathFromAsset()`, which calls it) waited on an `NSCondition` that a synchronous Photos request had already signalled, so it never returned. `saveImage()` ran on the main thread and waited the same way for Photos to finish writing, freezing the UI for the whole write and forever when Photos answered first. Reads no longer wait, and saves suspend off the main thread until Photos finishes; cancelling a save returns at once. A throwing `onImageSaved` no longer turns a completed save into a reported failure, and a throwing `onImageSavedFailed` no longer escapes `saveImage()`. Both callbacks now run on a background thread before `saveImage()` returns (previously the main thread).
- **Crash on Mac Catalyst during QR/barcode setup** (#70): the scanner assigned a fixed list of 13 metadata object types, but a Mac camera advertises far fewer (sometimes none). Assigning a type not in `availableMetadataObjectTypes` aborts the process (`NSInvalidArgumentException` in `_buildAndRunGraph`). CameraK now only ever assigns the intersection with the supported types, so QR scanning degrades gracefully on Mac/Catalyst instead of crashing. iPhone/iPad behavior is unchanged (all types remain supported). Note: this covers running an iOS app via Mac Catalyst; a native macOS (AppKit) target is not yet provided.
- **Desktop `RequestCameraPermission` and `RequestStoragePermission` called `onGranted` on every recomposition**: they call it once, from an effect.
- **The Android `rememberCameraKPermissionState` read its preferences file on the main thread**, in composition, on every resume and in the request's result: the request record is read and written on `Dispatchers.IO`, and until the first read finishes, just after the first resume, a permission that is not granted reads `NotDetermined`. The statuses and `onResult` are still published on the main thread.
- **iOS permission callbacks ran off the main thread**: `RequestCameraPermission` and `RequestStoragePermission` call back on the main queue, and `RequestStoragePermission` accepts limited Photos access, as `hasStoragePermission` does.
- **Android `CameraPreviewView` kept the first Activity's `PreviewView`**: it builds no view of its own any more, and renders the engine's preview in `CameraXViewfinder`, so a recreated Activity holds nothing of the destroyed one.

## [1.1] - 2026-06-30

### Fixed
- **Android photos cropped / reduced field-of-view** (#136): captured stills were zoomed-in vs the preview (e.g. a 4080×3060 sensor saved as a 3060×2295 centre crop). Cause: CameraK always bound a 16:9 `VideoCapture` use case in the photo `UseCaseGroup`, and the shared `ViewPort` had to fit every use case — so the 16:9 video shrank the common field of view for the 4:3 still (StreamSharing masked it only when 4+ use cases were bound). `VideoCapture` is now bound lazily — only while a recording is active — so photos use the full sensor field of view. A lens/device switch or a second `startRecording()` during recording is now rejected (they would tear down or orphan the live session), and a failed recording start rolls back so later photos stay full-FOV. Verified on a Galaxy S23 across photo/record/photo-after-record.
- **Android captured photo aspect ratio & orientation** (#136, follow-up): the 1.0 fix letterboxed the preview but, on real hardware, the **saved photo** still came out wrong — e.g. a portrait `RATIO_4_3` capture saved as a cropped 4:3 *landscape*. Root cause (found via on-device testing): three orientation sources disagreed — the capture rotation/EXIF was driven by the accelerometer while the ViewPort crop and preview followed the **display** rotation. Fixes: (1) the ViewPort `Rational` is now orientation-aware (portrait `RATIO_4_3` → 3:4) and rebuilt on a portrait↔landscape rotation; (2) capture `targetRotation` now follows the display rotation — the same source as the ViewPort and preview — so all three agree (WYSIWYG). Verified on a Galaxy S23 across all four ratios × both orientations × with/without the analyzer plugin (StreamSharing).
- **Android rotation during recording** (#147): a portrait↔landscape flip mid-recording no longer tears down the active recording. The ViewPort rebuild is deferred and applied when the recording finalizes; a recording that finalizes on error also clears its state so later rotations rebind correctly. `setTargetOrientation(null)` now reverts to the display rotation (consistent with auto mode) instead of a possibly-stale sensor orientation.

### Changed (behavior)
- **`targetResolution` no longer overrides `aspectRatio`** (Android): when both are set, the aspect ratio is the primary constraint and the resolution is the preferred size within it. Previously a target like `1920×1080` forced 16:9 output even when `RATIO_4_3` was requested.
- **Capture orientation in display-locked apps** (Android): an activity locked to one orientation now produces photos in that orientation (matching its preview) rather than sensor-rotated stills. Apps wanting sensor-based rotation should leave the activity orientation unlocked or use `setTargetOrientation()`.

## [1.0] - 2026-06-19

### Added
- **Opt-in logging (`CameraKLogger`)** (#133): internal logging is now disabled by default and routed through `CameraKLogger`. Set `CameraKLogger.enabled = true` to turn it on, or provide a custom `CameraKLogger.sink` to forward logs to your own logger.
- **`mirrorFrontCamera` configuration** (#112): optionally mirror front-camera captures to match the mirrored preview. Defaults to `false`. iOS and the Android byte-array path bake the flip into pixels; the Android file path records it as an EXIF orientation tag.
- **CI build check** (#129): a workflow builds all targets on every PR; merges are gated on passing checks and resolved review conversations.

### Changed
- **Better barcode/QR detection** (#130) on Android and iOS (stride-aware luminance, `TRY_HARDER`, inverted retry).
- **Android analyzer** now emits decodable JPEG frames (matching iOS) and runs off the main thread, fixing frame backpressure and `Could not decode ByteArray to Bitmap` consumers.
- **`setPreferredCameraDeviceType()`** now performs a live re-bind instead of requiring reinitialization.

### Removed (breaking)
- Deprecated `CameraController.takePicture()` (returned `ByteArray`) — use `takePictureToFile()`.
- Legacy callback-based `CameraPreview` API and the new/old API toggle.
- Dead `returnFilePath` flag and other removed-API references in docs. See the migration table in the README.

### Fixed
- **Plugin lifecycle leaks**: plugins could not remove what they registered, so listeners/outputs/analyzers accumulated on every camera re-init (lens switch, recompose), and coroutines/outputs leaked past detach. Fixes:
  - **Core**: added `CameraController.removeImageCaptureListener(...)` and iOS `safeRemoveOutput(...)` / `clearMetadataObjectsDelegate()`; `pluginScope` is now a StateHolder-owned child scope that `shutdown()` actually cancels (the old doc claimed this but never did); `attachedPlugins` access is synchronized and ignores duplicate attaches; `getReadyCameraController()` returns null on camera error instead of hanging forever.
  - **ImageSaverPlugin**: no longer double-saves after a re-attach (single listener, re-registered per Ready, removed on detach; saves run on `pluginScope`).
  - **AnalyzerPlugin / QRScannerPlugin / OcrPlugin**: each setup now returns a teardown handle; the plugin removes the prior analyzer/output before re-registering on a new Ready and on detach (Android `unregisterImageAnalyzer`, iOS `safeRemoveOutput` / cleared delegate, desktop cancels the collector scope) instead of stacking one per Ready. Frame/result flows are buffered (`DROP_OLDEST`) instead of spawning a coroutine per frame; `OcrPlugin.ocrFlow` is now a buffered channel that isn't closed on detach (so re-attach works) and OCR releases its ML Kit / Tesseract resources.
  - **VideoRecorderPlugin**: `startRecording()` while already recording is rejected instead of orphaning the timer/recorder; `shutdown()` now detaches plugins before resetting recording state so an in-flight recording is stopped (and emits `RecordingStopped`) before teardown; Android `stopRecording()` no longer hangs forever if the finalize event never arrives (5s timeout). iOS pause/resume and desktop pause limitations are now documented in code.
  - **Desktop `saveImage`**: writes to a real per-user directory (`~/Pictures` / `~/Documents`, honoring `customFolderName`) and respects `imageFormat`, instead of a relative dir literally named `PICTURES`; failures are logged and reported instead of silently swallowed.
- **iOS underexposed/black photos** (#138): `MemoryManager` compared `physicalMemory` to itself, so it reported 100% usage and `isUnderMemoryPressure()` latched on permanently. That made every capture downshift the session preset (`adjustSessionQuality`) synchronously right before `capturePhotoWithSettings`, capturing the still mid-reconfiguration before auto-exposure re-converged. Most visible on front-camera selfies; masked when a plugin (OCR/QR/Analyzer) kept an `AVCaptureVideoDataOutput` streaming. Memory pressure is now driven by the system memory-warning notification, and the capture no longer reconfigures the preset at shot time.
- **Android aspect ratio mismatch** (#136): a configured ratio (e.g. `RATIO_4_3`) no longer produces a photo that's a crop of the full-screen (≈16:9) field of view. The preview is now letterboxed to the configured ratio (`FIT_CENTER`) so its shared CameraX `ViewPort` matches the capture — preview FOV equals captured FOV. Adds `CameraController.getAspectRatio()`.
- **iOS preview/capture mismatch on flat devices** (#115, #109): preview no longer distorts when the device is face-up.
- **iOS crash from deprecated video stabilization API** (#113).
- **Android auto-save after capture**: capture listeners are now fired on `takePictureToFile()`.
- **Cross-analyzer buffer corruption**: the shared `ImageProxy` Y-plane buffer is duplicated before reads so concurrent analyzers aren't affected.
- **Desktop `takePictureToFile()`** now writes a real file instead of returning an empty path.
- **`ImageSaverPlugin.getByteArrayFrom()`** (Android) now reads raw file paths before falling back to `ContentResolver`.
- **Plugin initialization timing** (#52): null checks and graceful failure when the camera isn't ready yet.
- **Desktop Tesseract path resolution** (#51): dynamic tessdata lookup with graceful degradation.
- **Desktop QR scanner** (#50): fixed malformed decode-hints `EnumMap` initialization.
- **iOS image orientation** (#44): captures save in the correct orientation across portrait, landscape, and upside-down.
