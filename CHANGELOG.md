# Changelog

All notable changes to the Kamera project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.0] - Unreleased

### Removed (breaking)
- **No Intel iOS simulator artifacts**: the `iosX64` target is gone from every module, so 2.0 publishes klibs for `iosArm64` (devices) and `iosSimulatorArm64` (Apple-silicon simulators) only. Apps that still build for an x86_64 simulator must stay on 1.x or move their simulator builds to Apple silicon.
- **The core no longer supplies `androidx.camera:camera-extensions`** on Android, and no longer puts `androidx.activity:activity-compose` on consumers' compile classpath. Declare them if you use them directly.
- **`androidx.startup:startup-runtime` is gone from the core**, with CameraK's unused `AppContextInitializer` and its manifest provider. Apps that used androidx.startup only through CameraK must declare it.
- **ZXing is no longer exported by the core**: Android apps that used `com.google.zxing:core` through CameraK must declare it. `camerak-qr-scanner` no longer brings `com.google.zxing:javase` to desktop apps.
- **`kotlinx-atomicfu` is no longer exported** on the core's JVM and Android API.
- **`camerak-core` exports only `androidx.camera:camera-core` from CameraX** on Android: `camera-camera2`, `camera-lifecycle` and `camera-video` are `implementation`, and `camera-view` is no longer a dependency. An app that imports CameraX classes itself (`PreviewView`, `ProcessCameraProvider`, `Recorder`, `Camera2Interop`) declares those artifacts.
- **Only the release Android variant is published**; consumers' debug builds resolve the release AAR through variant matching.
- **iOS `MemoryManager` and `BurstCaptureManager` are removed, with no deprecation release before them**: the public object `com.kashif.cameraK.utils.MemoryManager` (`initialize`, `updateMemoryStatus`, `clearBufferPools`, `getBuffer`, `recycleBuffer`, `getOptimalImageQuality`, `isUnderMemoryPressure`) and the public class `com.kashif.cameraK.capture.BurstCaptureManager`. 1.x never deprecated them, so code that calls them stops compiling on 2.0 without a warning first. Nothing in CameraK used them; `MemoryManager.initialize` added a memory-warning observer on every `viewDidLoad` that was never removed, and `BurstCaptureManager` accepted captures and never ran them. The Android `MemoryManager` is removed too, with the rest of the 1.x camera API.
- **Kermit is no longer exported**: the core declared `co.touchlab:kermit` as an `api` dependency that nothing in CameraK imported (CameraK logs through `CameraKLogger`), which pinned every app's Kermit version. Apps that use Kermit declare it.
- **`video_recorder_plugin` is no longer published**: recording is part of the core. `VideoRecorderPlugin`, `rememberVideoRecorderPlugin` and the plugin's `startRecording(outputDirectory)`, `stopRecording()`, `pauseRecording()`, `resumeRecording()`, `recordingEvents`, `isRecording`, `isPaused` and `recordingDurationMs` are removed with no deprecation release. Call the holder's recording commands (see Added), read `CameraKStateHolder.recordingState`, and collect `CameraKEvent.RecordingEnded` from `events`; set the output directory in `VideoConfiguration.outputDirectory`.
- **`CameraKStateHolder`'s 1.x recording calls are replaced**: the deprecated `startRecording(configuration)`, `stopRecording()`, `pauseRecording()` and `resumeRecording()`, which returned `Unit` and reported only through events, are gone. The suspend commands of the same names return their outcome: `startRecording(config)` a `CameraKResult<RecordingState.Recording>`, `stopRecording()` a `CameraKResult<RecordedVideo>`, `pauseRecording()` and `resumeRecording()` a `CameraKResult<Unit>`. A call site that ignored the result must now call them from a coroutine.
- **ImageSaverPlugin's platform classes and its Coil dependency are removed**: `AndroidImageSaverPlugin` (with `getActualPathFromUri`), `IOSImageSaverPlugin` (with `getFilePathFromAsset`), `JVMImageSaverPlugin` (with its `onImageSaved` and `onImageSavedFailed` callbacks), `createPlatformImageSaverPlugin`, and `rememberImageSaverPlugin(config, context: coil3.PlatformContext)`. The saver no longer depends on Coil. Build it with `rememberMediaSaverPlugin(MediaSaverConfig { ... })` or `MediaSaverPlugin(config, platformContext: CameraKPlatformContext)`.
- **`CameraConfiguration.directory` is removed**: core writes every capture and recording to app-owned storage (see "Captures and recordings are app-owned files"), so the field chose nothing. The 1.x named-argument factory's hint says so and has no replacement for it; publish to the gallery with `MediaSaverPlugin`. `Directory` remains only as the type of that hint's parameter (see Deprecated).
- **The 1.x QR, OCR and analyzer plugin APIs are removed, with no deprecation release** (each plugin's 2.0 shape is under "Changed (breaking)"). QR: the coroutine-scope constructors, `ScannerHandle`, `getQrCodeFlow`, `attachToStateHolder`, `startScanning`, `pauseScanning` and `resumeScanning`, the `startScanning` extension on `CameraController`, desktop `QRScanner` and `GrayFrame`, Android `enableQrCodeScanner` and `QRCodeAnalyzer`, and iOS `ScannedCode` with the metadata delegate. OCR: the coroutine-scope constructor, `textFlow`, `ocrFlow`, `extractTextFromBitmap`, `attachToStateHolder`, `startRecognition` and `stopRecognition`, `RecognitionHandle`, `extractTextFromBitmapImpl` and iOS `VideoDataDelegate`. Analyzer: the coroutine-scope constructors, `AnalyzerHandle`, `startAnalyzer` (the plugin's and the `CameraController` extension), `stopAnalyzer`, `getAnalyzerFlow` and `attachToStateHolder`.
- **The 1.x camera API is removed, with no deprecation release beyond the hints under Deprecated**: `CameraController` on every platform, with all its constructors (those that take a `Directory` included), its listeners (`addImageCaptureListener`, `setOnOrientationChangedListener`, the iOS metadata delegate), the Android `registerImageAnalyzer` and `updateImageAnalyzer`, and the desktop `closeAndJoin()`; the 1.x facade machinery behind it; `CameraKState.Ready.controller`; `CameraKStateHolder`'s 1.x constructor `(cameraConfiguration, controllerFactory, coroutineScope)` and its `initialize()`, `getController()`, `getReadyCameraController()`, `emitEvent()`, `pluginScope` and `updateUIState()`; the ten 1.x `CameraKEvent` variants (`None`, `PermissionDenied`, `ImageCaptured`, `CaptureFailed`, `QRCodeScanned`, `TextRecognized`, `RecordingStarted`, `RecordingStopped`, `RecordingFailed` and `RecordingMaxDurationReached`), so the holder emits only `PluginFailed` and `RecordingEnded`; `CameraUIState.zoomLevel`, `maxZoom`, `imageFormat`, `qualityPrioritization`, `lastError`, `isRecording`, `isPaused` and `recordingDurationMs`; `CameraKPlugin.onAttach(stateHolder: CameraKStateHolder)`; `ImageCaptureResult.Success(ByteArray)`, `Rotation` and `InvalidConfigurationException`; `CameraCapabilities`' one-argument constructor; the Android `com.kashif.cameraK.utils.MemoryManager`; and the desktop `ImagePanel` and `ImageCaptureManager`. The iOS `CustomCameraController` (with its `CameraException` types) and `VideoRecordingDelegate` are internal. Build the camera with `CameraKStateHolder(config, platformContext, plugins)` or `rememberCameraKStateHolder`, issue its suspend commands, read `uiState`, `zoom`, `recordingState` and the commands' results, and implement `CameraKPlugin.onAttach(context: CameraKPluginContext)`.
- **The 1.x Compose API is removed** (camerak): `Permissions` and `providePermissions()` with their `RequestCameraPermission` and `RequestStoragePermission` members, which prompted as a side effect of composition (use `rememberCameraKPermissionState` and call `launchRequest()` from an event handler); `CameraPreviewView(controller)` (use `CameraPreview(holder)`); `LocalCameraKStateHolder`; and `DefaultLoadingScreen` and `DefaultErrorScreen`, which have no replacement: `CameraKScreen(holder)`'s slots draw nothing unless the app passes its own.
- **The media saver's 1.x API is removed**: `ImageSaverConfig`, `ImageSaveResult`, `rememberImageSaverPlugin(ImageSaverConfig, platformContext)`, `saveImage(ByteArray)`, `save(ByteArray, name)` and `readBytes(path)`. The saver publishes only files the camera wrote: save a capture with `save(image: CapturedImage, name)` or a recording with `save(video: RecordedVideo, name)`, and read a saved image with `readBytes(saved)`. `getByteArrayFrom(path)` is a hint (see Deprecated).
- **The desktop and platform utilities of 1.x are removed, with no hints**: the desktop `CameraGrabber` keeps only its `grabCurrentFrame()` hint (under Deprecated); its constructor, `start(scope, customGrabber)`, `setHorizontalFlip`, `stop`, `frameFlow`, `errorHandler` and `targetResolution` are gone or internal, as are the desktop `FrameConverter` (with `convert(Frame)`) and `OperatingSystem`; read frames from `holder.frames` and capture with `holder.capture()`. The Android `utils/Extensions.kt` (`getActivityOrNull`, `Bitmap.compressToByteArray`, `ImageProxy.toByteArray`) and the iOS `NSData.toUIImage`, `UIImage.fixOrientation` and `UIImage.toByteArray` are deleted with no replacement. The iOS `ByteArray.toNSData` and `NSData.toByteArray` stay, behind `@InternalCameraKApi`.

### Changed (breaking)
- **The core no longer exports Coil or Ktor** (was `api` on `io.coil-kt.coil3:coil-compose:3.5.0` and `io.coil-kt.coil3:coil-network-ktor3:3.5.0`, which brought the Ktor 3.1 client without an engine and registered a second Coil network fetcher). Nothing in the core used them. The media saver no longer depends on Coil either. Apps that used Coil's `AsyncImage`, its network loading or Ktor through CameraK must declare `io.coil-kt.coil3:coil-compose`, a `coil-network-*` artifact and Ktor themselves. On iOS, the media saver's read failures are `kotlinx.io.IOException`, the type Ktor's `IOException` already aliased.
- **Desktop apps add their own bytedeco natives** (was `org.bytedeco:javacv-platform` in the core, OCR and analyzer plugins). The libraries now depend only on the Java bindings they import: the core on `org.bytedeco:javacv:1.5.12` (without its transitive bindings), `javacpp:1.5.12`, `ffmpeg:7.1.1-1.5.12` and `videoinput:0.200-1.5.9`; `camerak-ocr` adds `tesseract:5.5.1-1.5.12` and `leptonica:1.85.0-1.5.12`. Measured over the external artifacts on each library's `desktopRuntimeClasspath` (before at 7557510, after at this release): the core's falls from 201 jars and 735.9 MB to 47 jars and 26.1 MB, `camerak-analyzer`'s the same, and `camerak-ocr`'s to 49 jars and 26.3 MB; the three together fall from 2,207.8 MB to 78.6 MB. The bytedeco share of each falls from 708.5 MB to 1.2 MB (1.5 MB for OCR). An app then adds the natives for each platform it ships, for example 24.4 MB for macOS arm64 with OCR (FFmpeg 19.4 MB, Leptonica 3.4 MB, Tesseract 1.6 MB, JavaCPP 0.04 MB). Apps must add the natives for the platforms they ship, either classifier jars such as `org.bytedeco:ffmpeg:7.1.1-1.5.12:macosx-arm64` (plus `javacpp`, and for OCR `tesseract` and `leptonica`; Windows captures through FFmpeg's dshow input, so it needs no `videoinput` natives) or the `-platform` artifacts narrowed with the `org.bytedeco.gradle-javacpp-platform` plugin; see the README's Desktop setup. Without natives the camera does not open: a `CameraKStateHolder` ends the start in `CameraKState.Error(CameraKError.NativeLibraryMissing)`, which names the bytedeco platform and keeps JavaCV's failure (`NoClassDefFoundError`, "Could not initialize class org.bytedeco.ffmpeg.global.avutil") as its cause, and the OCR plugin's calls throw `UnsatisfiedLinkError` the first time and `NoClassDefFoundError` after that. OpenCV, OpenBLAS, librealsense, libfreenect, FlyCapture, libdc1394 and ARToolKitPlus no longer arrive through CameraK; apps that used them transitively must declare them.
- **`camerak-analyzer` no longer depends on ML Kit text recognition, JavaCV or Tesseract**, none of which it used. Android apps that relied on ML Kit text recognition arriving through it must declare `com.google.mlkit:text-recognition` themselves, and drop the ML Kit data-collection disclosure if nothing else uses it.
- **Published under `dev.kashifmehmood`. The 1.x coordinates under `io.github.kashif-mehmood-km` relocate.** `dev.kashifmehmood` is the Gradle group and the published groupId of every module (the build's group was `com.kashif.*`); artifact ids and Kotlin packages do not change. `io.github.kashif-mehmood-km:camerak` and the four 1.x plugin ids are published at 2.0 as relocation POMs pointing at their 2.0 artifacts under `dev.kashifmehmood`, so switch both the group and the ids (`docs/migration/2.0.md`). Kotlin/Native klib unique names change with it, which matters only to libraries that compiled against a 1.x klib. An `includeBuild` of this repository still does not substitute the published coordinates on its own, because Gradle matches included projects by group and project name and the project names (`cameraK`, `ImageSaverPlugin`, ...) differ from the artifact ids (`camerak`, `camerak-media-saver`, ...); declare a `dependencySubstitution` for each artifact you include.
- **The plugins publish under their 2.0 artifact ids, and each 1.x id relocates to its successor**: `qr_scanner_plugin` is `camerak-qr-scanner`, `ocr_plugin` is `camerak-ocr`, `analyzer_plugin` is `camerak-analyzer` and `image_saver_plugin` is `camerak-media-saver`, all now in `dev.kashifmehmood`. Each 1.x id is published at 2.0 under `io.github.kashif-mehmood-km` as a POM-only artifact with a Maven `<relocation>` to the new group and id and no Gradle module metadata, so a build that declares the 1.x id resolves the 2.0 artifact (and Gradle and Maven report the relocation). Only the root ids relocate: a build that names a per-target id (`-android`, `-desktop`, `-iosarm64`, `-iossimulatorarm64`, or 1.x's `-iosx64`) rewrites it. `video_recorder_plugin` has no successor and no relocation. 2.1 stops publishing the relocations.
- **Plugin packages are lowercase, and the image saver is `MediaSaverPlugin`**: `com.kashif.ocrPlugin` is `com.kashif.ocrplugin` and `com.kashif.analyzerPlugin` is `com.kashif.analyzerplugin`; rewrite those two imports. Their class names do not change, and they leave no typealiases at the old names, because a package whose name differs only in letter case shares a directory with the new one on a case-insensitive disk. `com.kashif.imagesaverplugin` is `com.kashif.mediasaverplugin`, where `ImageSaverPlugin` is `MediaSaverPlugin` and `rememberImageSaverPlugin` is `rememberMediaSaverPlugin`, beside `MediaSaverConfig`, `GalleryDestination`, `SavedImage` and `SavedVideo`. The old saver names remain as ERROR-level typealiases, and `rememberImageSaverPlugin(config)` as an ERROR-level composable that throws, each with a quick fix to the new name; 2.1 removes them. The saver logs under the tag `MediaSaver`.
- **The OCR and analyzer plugins log under their own tags**: `camerak-ocr` logs under `TextRecognition` (was `CameraK`, the core's tag) and `camerak-analyzer` under `Analyzer` (was `AnalyzerPlugin`). Each artifact logs under exactly one tag, and the core under `CameraK`; update any log filter that matched the old tags.
- **Log messages no longer repeat their tag**: the core's messages no longer start with `CameraK:` and the OCR plugin's with `OcrPlugin:`, since the tag already names the artifact. A log filter that matched the prefix in the message text matches the tag instead.
- **The plugins' Android namespaces are their packages**: `com.kashif.qrscannerplugin`, `com.kashif.ocrplugin`, `com.kashif.analyzerplugin` and `com.kashif.mediasaverplugin` (were `com.kashif.qr_scanner_plugin`, `com.kashif.ocr_plugin`, `com.kashif.analyzer_plugin` and `com.kashif.image_saver_plugin`). No plugin has Android resources or an `R` class, so only the package in each AAR's manifest changes.
- **Android minSdk is 23** (was 21) for every module. 1.x already required 23 in practice: CameraX 1.5, Compose's Android artifacts, activity 1.13 and core-ktx 1.18 all declare minSdk 23, so an app at 21 or 22 failed its manifest merge. The build now checks that the declared minSdk equals the highest minSdk among the dependencies each library ships, and each library's unit tests merge their manifest at 23 and run their Robolectric tests at 23 as well as 35.
- **Built on Compose Multiplatform 1.11.1** (was 1.10.3). `camerak` exports Compose as `api`, so apps that use it resolve at least these versions (`camerak-core` has no Compose dependency); an app pinned to Compose Multiplatform 1.10 must upgrade with CameraK 2.0.
- **Captures and recordings are app-owned files on every platform**: every capture and recording is written to `CameraConfiguration.outputDirectory` (a recording's own `VideoConfiguration.outputDirectory` first), used as given, else `filesDir/CameraK` on Android, `Documents/CameraK` on iOS, and on desktop `~/Documents/CameraK` for photos and `~/Movies/CameraK` (macOS) or `~/Videos/CameraK` (Linux, Windows) for videos. Nothing checks that an `outputDirectory` is app-owned. The configuration's `directory` is gone (see "Removed"): the core no longer inserts into MediaStore, runs the media scanner (#158) or imports into Photos. On Android, photos and default-location videos move from `getExternalFilesDir(null)/CameraK` and the public `Pictures`, `DCIM` and `Movies` folders to internal `filesDir/CameraK`; on iOS captures and recordings move from the Photos library to `Documents/CameraK`. Existing files are not moved. Apps that relied on captures appearing in the gallery save them with `MediaSaverPlugin` (auto-save or `save()`).
- **Android capture file names** change from `<prefix>_yyyyMMdd_HHmmss.<ext>` to `<prefix>_<epoch ms>_<8 hex>.<ext>`, for photos, videos, gallery entries and the media saver's default names, so two captures in one second no longer collide. A capture whose file cannot be created returns a `Failure` instead of throwing.
- **Android `ImageFormat.PNG` captures are PNG files**: CameraX's file output always encodes JPEG, so the engine decodes it, turns it upright by its EXIF orientation and writes a PNG on a background executor, then deletes the JPEG. The media saver on Android labels saved images by their actual bytes.
- **The core's manifest merges `android.permission.CAMERA`** and `uses-feature` entries for `android.hardware.camera.any`, `camera`, `camera.autofocus` and `camera.flash`, all `required="false"`. Google Play therefore no longer infers a required back camera with autofocus from CAMERA; an app that needs one declares the feature `required="true"` itself (the merger ORs `required`).
- **Android `QualityPrioritization.NONE` always captures with `CAPTURE_MODE_MAXIMIZE_QUALITY`**, the same as `QUALITY`. Before, it dropped to `MINIMIZE_LATENCY` whenever device-wide RAM use went above 80%.
- **External cameras are listed apart**: `LensInfo` gains `isExternal: Boolean = false` (source compatible; the data class's binary signature changes). `CameraCapabilities.lenses(lens)` and `availableDeviceTypes(lens)` leave out external cameras, which the new `CameraCapabilities.externalLenses` lists. On Android, `LENS_FACING_EXTERNAL` cameras report `lens = BACK` with `isExternal = true`. Selecting one by `cameraId` opens it (see Fixed).
- **Desktop `AspectRatio.RATIO_9_16` is the 16:9 frame**: desktop cropped each frame to a 9:16 strip for `RATIO_9_16`, where Android and iOS already treated it as `RATIO_16_9` with the device's orientation deciding portrait or landscape. Desktop now does the same, so a `RATIO_9_16` preview, photo, recording and analysis frame on desktop is 16:9 (see Deprecated).
- **`LensInfo` is a plain class**, not a data class: it keeps its eight constructor parameters and compares, hashes and prints by value, but `copy()` and `component1()` to `component8()` are gone. **`CameraCapabilities` compares by value** (before, by identity): two capabilities are equal when every lens and every reported mode and format is equal.
- **`ImageFormat.HEIC`** (`heic`, `image/heic`) is a new entry, so an exhaustive `when` over `ImageFormat` needs a branch for it. iOS writes HEIC where the bound camera's photo output offers HEVC, and lists it in `supportedImageFormats` only there; elsewhere an iOS HEIC capture returns `Unsupported(IMAGE_FORMAT)` without taking a photo, logged once. Android and desktop do not write HEIC: a camera configured with it fails its start with `Unsupported(IMAGE_FORMAT)` before anything binds or opens, and nothing is written.
- **Android lens device types are relative to the main lens**: each lens of a facing is compared with that facing's main lens, the largest readable sensor among the single-focal lenses between 20 mm and 70 mm (35 mm equivalent; a tie goes to the shorter lens). A lens at 1.6x the main lens's equivalent focal length or more is `TELEPHOTO`, one at 0.75x or less `ULTRA_WIDE`. Before, only absolute thresholds counted (20 mm or less ultra-wide, 70 mm or more telephoto), so a 2x telephoto beside a 24 mm main lens was reported as `WIDE_ANGLE`; `CameraDeviceType.TELEPHOTO` can now select a lens it did not select in 1.x. A facing with no main lens, and a lens whose sensor width is unreadable, still use the absolute thresholds.
- **`CameraConfiguration` and `VideoConfiguration` are built with a DSL**: `CameraConfiguration { flashMode = FlashMode.AUTO }` and `VideoConfiguration { maxDuration = 30.seconds }`. Neither is a data class any more: a private constructor, a `Builder` receiver whose every default is the 1.x default, `copy { }` in place of the data-class `copy(...)`, no `componentN`, and `equals`, `hashCode` and `toString` over every field. `CameraConfiguration()` and `VideoConfiguration()` are the defaults. The 1.x named-argument calls no longer compile: each is an ERROR-level deprecation whose quick fix writes the DSL call. `targetResolution` is a `Resolution` (was `Pair<Int, Int>`). Fields new in 2.0, each defaulting to 1.x behaviour: `cameraId: String? = null`, `outputDirectory: String? = null`, `frameAnalysis = false`, `analysisResolution: Resolution? = null`, `analysisFormat = FrameFormat.YUV_420`, `initialZoomRatio = 1f` (clamped into the camera's range) and `targetOrientation: DeviceOrientation? = null` (follows the device). `analysisResolution` is the nearest supported size on Android, scales and centre-crops each frame on desktop, and is a preference on iOS, where analysis frames come at the session's size.
- **A configuration with no lens opens the platform default camera**: `CameraConfiguration.cameraLens` is a `CameraLens?` and defaults to `null` (was `BACK`). Null is the back camera on Android and iOS, and on desktop the system default device: on macOS the one `AVCaptureDevice.defaultDeviceWithMediaType:` names (avfoundation `"0"` only when enumeration fails), elsewhere the first enumerated device, so an external webcam FFmpeg lists first no longer wins over the built-in camera. Code that reads `cameraLens` handles null.
- **A zero or negative `Resolution` is rejected when the configuration is built**: a `targetResolution` or `analysisResolution` with a width or height of 0 or less throws `IllegalArgumentException` naming the field. Before, desktop logged an unusable analysis size once per session and skipped analysis.
- **`VideoConfiguration` validates its limits, and its limits are nullable**: `maxDurationMs: Long` becomes `maxDuration: Duration?` and `maxFileSizeBytes` (new in 2.0) is a `Long?`; `null` means unlimited for both (was `0`). A negative `maxDuration` or `maxFileSizeBytes` throws `IllegalArgumentException`; before, a negative value meant unlimited. `filePrefix` must be 1 to 64 characters from `A-Z a-z 0-9 . _ -` and not `.` or `..`, or the constructor throws. `enableAudio` defaults to `false` (was `true`): a recording asks for the microphone only when the app sets it. On Android the CameraX Recorder enforces both limits, and a positive `maxDuration` under 1 ms is applied as 1 ms, since CameraX reads 0 as unlimited.
- **Desktop capture locations**: photos land in `~/Documents/CameraK`, or `CameraConfiguration.outputDirectory`, instead of `java.io.tmpdir`. Videos without an `outputDirectory` go to `~/Movies/CameraK` (macOS) or `~/Videos/CameraK` (Linux, Windows), not a working-directory `captured_videos` folder. A folder the camera creates is `rwx------` and each photo `rw-------` where POSIX permissions exist.
- **Desktop recording runs on the engine**: it stops at `VideoConfiguration.maxDuration` (paused time left out) and at `maxFileSizeBytes`, pauses and resumes, records all four `VideoQuality` values at the size of the frame the preview shows (the camera's frame, cropped to the configured aspect ratio under the holder's engine) and the quality's bitrate (`VideoQuality` sets only the bitrate, no longer the width and height), and keeps a file only when it plays (a frame written and the container closed); an unplayable file is deleted and the recording fails. The recorder reads the camera's frames without copying each one, and records each as a JavaCV `Frame` over the preview's own BGR24 buffer: the recording adds no conversion or copy of its own (no `BufferedImage` round trip), and the frame the preview, stills and analysis share is still blitted once. On a synthetic 1280x720 source into the H.264 MP4 recorder it recorded 54.6 to 56.0 fps against 53.0 to 54.0 fps with the per-frame conversion (about +4%, three 5 s runs each, back to back); the encoder dominates. `close()` waits at most 5 s for a recorder to stop; past that the recording ends with `Timeout(RECORD_STOP)` and reason ERROR, and the camera is released. With `VideoConfiguration.enableAudio = true` the holder's `startRecording` and `prepareRecording` return `Failure(Unsupported(AUDIO))` before any recorder opens. `selectCamera` during a recording is `Busy(DEVICE_TYPE)` when the switch keeps the lens, as the holder decides, so also between two BACK webcams of the same type, and `Busy(LENS)` otherwise; a silent switch between them times out as `Timeout(DEVICE_TYPE)`. A camera faster than 30 fps is recorded at 30 fps.
- **Desktop preview letterboxes to the frame's aspect ratio**, not the configured `CameraConfiguration` ratio (which is used only until the first frame). The overlay's box is that letterboxed frame, so overlay coordinates change.
- **Desktop frames are cropped to the configured aspect ratio under the holder's engine**: each camera frame is cut to `CameraConfiguration.aspectRatio`, centred, with an even cut side so H.264 takes it, and mirrored when `mirrorFrontCamera` is set and the camera is FRONT (never a BACK camera), in one draw, so the preview, stills, recordings and analysis frames see the same pixels. A 4:3 webcam under the default 16:9 configuration now gives 16:9 photos and videos.
- **Desktop default camera on Linux** is the lowest-numbered V4L2 node (sorted numerically) that udev records as capture-capable, or without a udev record the lowest-numbered node with sysfs index 0. A machine whose first node by name was `video10`, a metadata node or a non-capture node now opens a different device.
- **Desktop media saver names and folders**: with no folder name (`MediaSaverConfig.folderName`, 1.x `customFolderName`), images go to `~/Pictures/CameraK` (PICTURES, DCIM) or `~/Documents/CameraK` (DOCUMENTS), as on Android and as CameraK's desktop captures do, instead of straight into `~/Pictures` or `~/Documents`. A save's `name` and the `folderName` must each be 1-64 characters from `[A-Za-z0-9._-]` and not `.` or `..`; `save(image, name)` with any other name throws `IllegalArgumentException`. The auto-save prefix may be at most 50 such characters; on every platform a `MediaSaverConfig` with any other prefix or folder name throws `IllegalArgumentException` when it is built, instead of failing every save. An output folder that is a symbolic link fails with an `IOException`, wherever the link points, including to a folder beside it in the same directory. A save never overwrites: a taken name gets a numeric suffix (`shot_1.jpg`), and unnamed saves are `image_<yyyyMMdd_HHmmss_SSS>`. The captured file is copied unchanged.
- **The desktop media saver reads only its own folders**: `readBytes(saved)` reads only files that resolve, after `..` and symbolic links, into the saver's own folder (`<destination>/<folderName or CameraK>`) or into `~/Pictures/CameraK` or `~/Documents/CameraK`, where desktop captures go. The user's other files in Pictures and Documents are refused, and a CameraK or custom folder that is itself a symbolic link, even one pointing at Pictures, Documents or a folder inside them, is not read. Any other path, and any read failure, fails with an error whose message contains no path, and a failed save is logged without its path.
- **The image saver is the 2.0 media saver, `MediaSaverPlugin`** (Decision 10): a final class, `MediaSaverPlugin(config: MediaSaverConfig, platformContext: CameraKPlatformContext)` (was the abstract `ImageSaverPlugin`, with a subclass per platform), configured by `MediaSaverConfig { autoSave; prefix; destination; folderName; imageFormat }` with `GalleryDestination.PICTURES`, `DCIM` or `DOCUMENTS`. `save(image: CapturedImage, name)` and `save(video: RecordedVideo, name)` copy the app-owned file into the gallery without decoding or changing it and return `CameraKResult<SavedImage>` or `CameraKResult<SavedVideo>`, and `readBytes(saved)` reads a saved image back. On Android a save is a pending MediaStore row in `MediaStore.Images`, `MediaStore.Video` or, for DOCUMENTS, `MediaStore.Files`, deleted again when the copy fails; on iOS it is one Photos import off the calling thread, bounded at 60 s, whose failure is `Storage(GALLERY_IMPORT_FAILED)` with the file kept; on desktop it is a copy into `~/Pictures/<folder>` or `~/Documents/<folder>`. The saver needs no analysis frames, so it binds no frame analysis.
- **The media saver checks the gallery permission and shows no prompt**: every save first reads `GALLERY_ADD` where the platform needs it (`galleryPermission`: iOS, and Android API 28 and below; null on Android API 29 and later and on desktop) and returns `Failure(Permission(GALLERY_ADD, status))` without touching the gallery unless it is Granted or Limited. iOS also saves at NotDetermined, where Photos shows its add-only prompt during the save (below iOS 14 too), and a prompt refused then is `Permission(PermanentlyDenied)` or `Permission(Restricted)`. The app requests `galleryPermission` itself.
- **The media saver auto-saves the holder's captures**: with `MediaSaverConfig.autoSave` it saves every capture that reaches `CameraKStateHolder.captures`, that is every successful `capture()`, and emits each outcome on `results`. A failed auto-save is a `Failure` on `results`, logged once with its cause and no path; it no longer emits `CameraKEvent.PluginFailed`, the plugin stays Running, and the next capture is saved.
- **`WRITE_EXTERNAL_STORAGE` moves from the core's manifest to `camerak-media-saver`'s**, still with `maxSdkVersion="28"`. An app that writes to shared storage below API 29 without the saver declares it itself.
- **Desktop OCR language data**: Tesseract data is no longer searched for in the working directory or the repository tree. Set `OcrConfig { tessdataPath = ... }`, package the pinned `eng.traineddata` at `com/kashif/ocrplugin/tessdata/` (the 1.x path `com/kashif/ocrPlugin/tessdata/` is still read, with one warning to move it), or set `TESSDATA_PREFIX`. The pinned model ships as its own artifact, `camerak-ocr-tessdata-eng` (Tesseract's `eng.traineddata`, Apache-2.0, 23 MB), which puts it at that classpath path; `camerak-ocr` does not depend on it, so a desktop app adds it to ship the model. With no data, live OCR's status is `Failed` and `recognize` returns a `Failure`, instead of every scan logging and returning null. `tessdataPath` is ignored on Android and iOS.
- **The QR, OCR and analyzer plugins share one 2.0 shape**: each is a `CameraKPlugin` built from its config (`QRScannerPlugin(config)`, `OcrPlugin(config)`, `AnalyzerPlugin(config)`, or `rememberQRScannerPlugin(config)`, `rememberOcrPlugin(config)`, `rememberAnalyzerPlugin(config)`), passed to the holder, with `status: StateFlow<PluginStatus>` (`Idle`, `Running`, `Paused`, `Failed`), `results: Flow<...>` that never holds up the camera (the oldest unread result is dropped), and `pause()` / `resume()`, where a pause holds across camera sessions. Each reads the holder's shared analysis frames through one asynchronous registration that retains no frame, accepts `YUV_420` and `RGBA_8888`, and reads the frame's copied planes, never `CameraFrame.pixelBuffer`; none adds a capture output of its own. Its rate is the registration's `maxFps`, applied by the frame source. A failure is logged with its throwable and reported once as `CameraKEvent.PluginFailed`, and the plugin's status becomes `Failed`. Each config is a builder class, not a data class.
- **QR scanning** (`camerak-qr-scanner`): `QRScannerConfig { formats = setOf(BarcodeFormat.QR_CODE); region: FrameRect? = null; dedupeWindow = 1.seconds; maxFps = 5f }` (5 a second matches 1.x's 200 ms) and `results: Flow<Barcode>`, `Barcode(rawValue, rawBytes, format, boundingBox)` in frame pixels. The payload is attacker-controlled, as its KDoc says, and is left out of `toString`. The same format and payload are reported once per `dedupeWindow`, on every platform. `BarcodeFormat` is an open value class (`QR_CODE`, `AZTEC`, `DATA_MATRIX`, `PDF_417`, `EAN_13`, `EAN_8`, `UPC_A`, `UPC_E`, `CODE_128`, `CODE_39`, `CODE_93`, `CODABAR`, `ITF`), so 2.x can add entries; a format the platform cannot read (iOS Vision has no `UPC_A`) is logged once when the plugin is made and ignored. Android and desktop decode with ZXing, iOS with Vision, all from the frame's luma, so an `RGBA_8888` session decodes too, and turned upright by the frame's rotation, so a 1D barcode in a portrait frame decodes (#168). The plugin no longer posts `CameraKEvent.QRCodeScanned`. Before 2.0 ships, the iOS "preview with analysis" budget for QR on Vision is measured on a device (release gate B1); if it misses, iOS QR decodes from a core-owned metadata output before the release.
- **Text recognition** (`camerak-ocr`): `OcrConfig { maxFps = 2f; region: FrameRect? = null; level = OcrLevel.FAST; tessdataPath: String? = null }`, `results: Flow<RecognizedText>`, and `suspend recognize(image: CapturedImage, level = OcrLevel.ACCURATE): CameraKResult<RecognizedText>` for a still, which runs off the caller's thread, releases the recognizer however it ends, returns `Failure(Internal)` instead of throwing, and does not log the text. `RecognizedText(text, blocks, timestampNanos)` joins its `TextBlock(text, bounds, confidence)` blocks with newlines; bounds are in frame pixels. `OcrLevel` is an open value class, `FAST` or `ACCURATE`: Vision's two levels on iOS, Tesseract's legacy engine (or its default when the data has none, logged once) and LSTM engine on desktop, ignored by ML Kit's single model. Live recognition reads at most `maxFps` frames a second on every platform, only inside `region`, and no longer posts `CameraKEvent.TextRecognized`. The unbundled ML Kit model is deferred to 2.1.
- **Frame analysis** (`camerak-analyzer`): `AnalyzerConfig { maxFps = 1f; maxDimension: Int? = 1280; jpegQuality = 80 }` and `results: Flow<EncodedFrame>`, `EncodedFrame(bytes, width, height, rotationDegrees, timestampNanos)`: an owned JPEG per analysed frame on every platform (desktop emitted the raster's raw BGR array in 1.x), its longest side scaled down to `maxDimension` with the aspect ratio kept and never scaled up (null keeps the full size). A `maxFps`, `maxDimension` or `jpegQuality` (1 to 100) out of range throws `IllegalArgumentException` when the config is built. The plugin registers for frames only while `results` has a collector, so it encodes nothing when nobody reads.
- **Plugin results no longer reach `CameraKStateHolder.events`**: the QR and OCR plugins post no `QRCodeScanned` or `TextRecognized`; collect the plugin's `results`.
- **iOS flash and torch follow the configuration**: the configured `FlashMode` reaches captures (before, `FlashMode.OFF` could still fire the flash) and the configured torch is applied whenever the session starts and after every lens or device-type switch.
- **iOS lens switch during a recording is refused**: `selectCamera` returns `Busy` while recording, instead of stopping the session and cutting the recording. A camera input the session refuses keeps the previous camera instead of leaving the session without one.
- **iOS session presets keep the configured aspect ratio** (#161, #171): 4:3 and 1:1 run the Photo preset, then 640x480; 16:9 and 9:16 run 3840x2160, 1920x1080, then 1280x720. A preset of another ratio, or `High`, is never chosen, so a 4:3 configuration with a 1920x1440 target no longer runs 1920x1080. A `targetResolution`, portrait or landscape, starts the list at the smallest preset of that ratio that reaches it (the largest when none does), and a preset the session cannot take falls back to the next one of its ratio instead of crashing. Without a target every ratio runs the Photo preset: a 16:9 or 9:16 still is a centred crop of the full-resolution photo and a 1:1 still a centred square, with the photo's metadata and EXIF orientation kept (about 20 ms for a 12 MP photo on the simulator). The preview fills a centred box of the configured ratio with `AVLayerVideoGravityResizeAspectFill`, so it shows what the still keeps. While a recording runs its quality's preset, a 4:3 still is cropped to 4:3.
- **iOS outputs are attached on demand**: the movie file output is attached only for a recording, and CameraK attaches no metadata output. The first `startRecording` pays one session reconfiguration, and the microphone input is removed when the recording ends.
- **iOS runs overlapping captures**: a capture started while another is processing runs instead of failing with "Capture in progress". `QUALITY` captures are sized with `maxPhotoDimensions` instead of the deprecated high-resolution flags.
- **Captures are no longer rejected with "Burst queue full"** on Android and iOS: the holder's `capture()` allows three in flight and returns `Failure(Busy(CAPTURE))` for a fourth.
- **iOS orientation**: `setTargetOrientation` sets the photo's orientation, as documented, and no longer rotates the preview. The preview follows the interface (window scene) orientation instead of the device orientation, so portrait-locked apps keep an upright preview.
- **iOS recording lifecycle**: `startRecording` returns once AVFoundation has started recording (before, it returned the running recording's path while one was in progress). `pauseRecording` returns `Unsupported(PAUSE_RESUME)` below iOS 18 (before, it silently kept recording) and a `Hardware` failure when the output does not confirm the pause.
- **iOS recording outcome and location**: a recording keeps its file only when the file plays. A file AVFoundation reports as not successfully finished is a success, with the end's reason, when it plays; otherwise it is deleted and the recording fails with `Hardware` and the `NSError` as cause (1.x returned `Success`). A full disk that left a playable file is `Storage(FULL)` with that file kept. A recording keeps 200 MB of disk free and stops at `VideoConfiguration.maxDuration` and `maxFileSizeBytes` when they are set.
- **iOS recording on the engine**: the session runs the `VideoConfiguration.quality`'s preset (SD 640x480, HD 1280x720, FHD 1920x1080, UHD 3840x2160) from the movie's start and returns to the still preset after the recording finishes. With `enableAudio` and no `NSMicrophoneUsageDescription` in the app's Info.plist, the start is `Unsupported(AUDIO)` before any microphone call. A video-only recording never touches the app's `AVAudioSession`: CameraK configures it only while an audio recording is configured. A microphone the session refuses is logged and the recording goes on without audio, with `hasAudio` false.
- **iOS recording starts that time out leave nothing behind**: a start AVFoundation reports only as the 5 s start timeout fires is stopped (reason ERROR) and finalized, and the start returns `Timeout(RECORD_START)`; the file AVFoundation writes for a start already abandoned is deleted.
- **iOS front `CameraDeviceType.DEFAULT` is the built-in ultra-wide camera where the front camera is one** (iPhone 17, #170, #175), then the wide-angle; the back camera's DEFAULT is still the wide-angle.
- **iOS analysis frames are YUV_420 only**: `supportedAnalysisFormats` is `{YUV_420}`, and a configuration with `analysisFormat = RGBA_8888` fails its start with `Unsupported(ANALYSIS_FORMAT)`.
- **iOS 17 and later rotate captures and the preview with `AVCaptureDevice.RotationCoordinator`**: photos and movies take the target orientation when one is set, otherwise the horizon-level capture angle, and the preview layer takes the coordinator's preview angle, so a 180° turn of the device, which brings no layout pass, turns it. Below iOS 17 captures follow the device orientation, keeping the last valid one while the device lies flat (#109, #115).
- **iOS PNG captures keep the original pixels and metadata**: they keep the sensor's pixel layout and carry the EXIF orientation as metadata, instead of being redrawn upright without an orientation tag.
- **`CameraKState` is the 2.0 lifecycle**, a closed `sealed interface`: `Idle`, `Starting`, `Ready`, `Interrupted(reason: InterruptionReason)`, `Error(error: CameraKError)` and `Closed` (was a sealed class of `Initializing`, `Ready(controller, uiState)` and `Error(exception, message, isRetryable)`). An exhaustive `when` needs the new branches. `Ready` is a `data object`: it carries no `uiState` (read `CameraKStateHolder.uiState`) and no controller (issue commands on the holder). `Error` carries the typed `CameraKError`, with the platform's cause, in place of `exception` and `message`; `isRetryable` is the error's. `Interrupted` means the platform holds the session and resumes it on its own (a call, multitasking, another app holding the camera).
- **`CameraKStateHolder` runs on the platform's camera engine** and owns its coroutine scope. `CameraKStateHolder(config, platformContext, plugins)` builds it over the platform engine; `start()`, `stop()`, `retry()`, `recheckPermission()`, `close()` and `suspend closeAndJoin()` drive it, and `cameraState` reaches `Ready` only once the platform reports the camera open. Before opening it asks the environment's permission checker and publishes `Error(Permission)` when the camera is not granted; the production constructor's checker reads the platform's status (Android's grant and recorded requests, AVFoundation and Photos on iOS, macOS's camera authorization on desktop, Granted on Linux and Windows), so a denied camera is `Error(Permission)` instead of a failed open. A start the platform does not answer within 10 s ends in `Error(Timeout(START))`, or in `Error(Permission(NotDetermined))` while the permission is still undetermined (a platform that prompts on open), a runtime failure stops the camera and ends the session in `Error`, and `close()` publishes `Closed`, detaches the plugins, then closes the engine, waiting at most 5 s for it.
- **`camerak` exports `org.jetbrains.androidx.lifecycle:lifecycle-runtime-compose`** 2.9.6 (`api`), whose `LifecycleOwner` `rememberCameraKStateHolder`'s signature names. `rememberCameraKState` is a hint (see Deprecated).
- **A recording quality the bound camera does not offer fails the start** on Android and iOS: the holder's `startRecording` returns `Failure(Unsupported(VIDEO_QUALITY))`, where 1.x silently recorded at another quality. Check `CameraCapabilities.supportedVideoQualities` for the bound camera. On Android, when the camera's quality set cannot be read (the query throws or CameraX reports none), the recording falls back as 1.x did, to the requested quality or the next lower, else the next higher, and `supportedVideoQualities` is empty.
- **Android recording follows CameraX's milestones**: `startRecording` returns once CameraX reports the recording started; a recording CameraX finalizes before it started fails the start, and its file is deleted even when it plays. `pauseRecording` and `resumeRecording` return once CameraX confirms, or `Timeout`. A finished file is kept only when it plays: an unplayable one fails the recording and is deleted. A full disk that left a playable file is `Storage(FULL)` with the file kept. The Recorder's target bitrate is the quality's.
- **Android camera errors are typed**: CameraX camera states map to the session's state. A recoverable error is `Interrupted` (`IN_USE_BY_ANOTHER_CLIENT` for a camera in use or too many open cameras, `OTHER` otherwise) and becomes `Error(Hardware)` when CameraX has not recovered within 10 s; a stream-configuration error is `Unsupported(ASPECT_RATIO)`, or `VIDEO_QUALITY` when the bind included video; a disabled camera or Do Not Disturb is `CameraDisabled`; any other critical error is `Hardware` with CameraX's code and cause. `stop()` keeps the use cases bound, so the next start reopens without a rebind; `close()` unbinds only CameraK's own use cases. The orientation sensor runs only while the session is started. `camerak-core` on Android depends on `androidx.tracing:tracing` 1.2.0 (runtime scope; CameraX 1.5.3 already brings it) and writes `CameraK.start` and `CameraK.firstFrame` trace sections.
- **iOS 16 is the minimum**: below iOS 16 the camera makes no session and every engine call returns `Unsupported(PLATFORM_VERSION)`, so the holder ends its start in `Error`. `QUALITY` captures are sized with `maxPhotoDimensions` only; the high-resolution-flag fallback is gone. The README, the installation guide and the migration guide state the iOS 16.0 deployment target.
- **iOS session errors are typed and keep the `NSError`**: every `AVCaptureSessionInterruptionReason` maps to an `InterruptionReason` (anything unknown is `OTHER`); a media-services reset is `Interrupted(MEDIA_SERVICES_RESET)` and restarts the session, again after every restart that ran, while a reset before the restart ran, or a restart after which the session does not run within 10 s, ends in `Error(Hardware)`; a device used by another session is `CameraInUse`, a disconnected device `Disconnected`, an unauthorized app `Permission(CAMERA, PermanentlyDenied)`, a session that is not running `NotReady`, and any other error `Hardware` with its code. The `NSError` is each error's cause. Start and first-frame intervals are written as `os_signpost` intervals named `CameraK`.
- **Desktop camera errors are typed**: missing bytedeco natives are `NativeLibraryMissing` with the natives' platform name (for example `macosx-arm64`), a busy device (`EBUSY`) is `CameraInUse`, a camera macOS denies or restricts is `Permission`, and any other failure is `Hardware` with FFmpeg's code. When the camera will not open at CameraK's size and frame rate, the open is retried once at the camera's own mode. After the camera opens, a failed grab or no frame for 5 s is `Interrupted(OTHER)` while the engine reopens the camera with backoff, and `Error(Disconnected)` after 10 s. A stop interrupts a grab the camera driver leaves sleeping. On macOS the camera authorization is read through JNA when the app ships `net.java.dev.jna:jna` (CameraK declares it compile-only, so no classpath changes); without it the status reads as not determined.
- **`CameraKStateHolder` commands are suspend functions that return the applied value**: `capture(): CameraKResult<CapturedImage>`, `setZoom(ratio): CameraKResult<ZoomState>`, `setFlashMode`, `setTorchMode`, `selectCamera(lens, deviceType)`, `selectCamera(id)` and `setTargetOrientation`, replacing the non-suspend `setZoom`, `setFlashMode`, `setTorchMode` and `setTargetOrientation` of the same names. Outside `Ready` a command returns `NotReady`, after `close()` `Closed`, and a thrown exception `Internal`. `setZoom` returns the ratio clamped into the camera's range, and while one zoom or orientation call is in flight a newer one replaces any pending call, whose callers get the newer call's result. A fourth capture in flight is `Busy(CAPTURE)`. Every successful capture also reaches `captures` (a `SharedFlow` buffered to 64), a cancelled caller's included; `zoom` and `capabilities` are the engine's flows. `close()` detaches the plugins, lets running commands finish for up to 2 s, then closes the engine.
- **`CameraKStateHolder.uiState` is derived from what the platform reports**: flash, torch, lens, device type and zoom follow the bound camera, so a command shows there only once the platform has applied it, and it no longer goes stale after `close()`. `CameraUIState` gains `pendingCaptures`, `cameraId` and `targetOrientation`; `cameraLens` is null before the first bind; `isCapturing` is `pendingCaptures > 0`; `CameraUIState` is a plain class with an internal constructor that compares by value (was a data class), without its 1.x fields (see Removed). `events` is buffered to 64, dropping the oldest.
- **`CameraKEvent` is an abstract class with an internal constructor** (was a sealed class), so CameraK can add events in a minor release: a `when` over an event needs an `else` branch, and apps cannot create events. **`CameraKEvent.PluginFailed` carries `pluginId: String` and `error: CameraKError`** (was a data class over `error: Throwable`): the plugin's `id` (by default its class's simple name), and the throwable as `CameraKError.Internal`'s `cause`. Its constructor is internal.
- **Engine hardware commands answer `NotReady` until the camera is open**: `setFlashMode`, `setTorchMode` and `setZoom` on every engine, the fake included, return `NotReady` in every state but Open (the desktop engine's `setFlashMode(OFF)` used to succeed before Open). `setTargetOrientation` is configuration: every engine accepts it in any state before `close()`, applies it at the next bind or capture, and returns `Closed` after.
- **Android flash, torch and zoom are read back from CameraX**: `hardware` follows the bound camera's torch and zoom state, and the flash is read from the bound `ImageCapture` after every set and bind. Flash `ON` or `AUTO` and torch `ON` on a camera without a flash unit, and torch `AUTO` on any camera, are `Unsupported`; `setZoom` clamps to the range CameraX reports, which can start below 1x, and a fixed-zoom camera refuses any other ratio with `Unsupported(ZOOM)`. Capabilities take a bound camera's flash support from `CameraInfo.hasFlashUnit` and list torch `OFF` and `ON` only. The configured or previously set torch and zoom are applied once the camera opens, where the first start used to lose them. With `CameraConfiguration.frameAnalysis = true` the first bind includes the analysis, so a plugin that needs frames no longer causes a second bind at start. A display rotated while the camera is stopped is applied at the next start, which rebinds when the orientation category changed. A lens without a flash unit binds flash `OFF` and reports `OFF`; the mode last requested is bound again on the next lens with a flash, as 1.x did. `selectCamera` is written as a `CameraK.lensSwitch` trace section.
- **iOS flash, torch and zoom are read back from the device**: torch and zoom follow the device by key-value observing, and a torch that is on but dark (thermal shutoff) is reported `OFF`; the flash is the photo output's validated mode. `setZoom` clamps into the device's range before the device sees it, and the range ends at `maxAvailableVideoZoomFactor`. A fixed-zoom camera refuses any other ratio, and a torch mode the device does not offer is `Unsupported(TORCH)`, and a configuration lock the device refuses returns `Hardware`. Torch modes per lens come from the device. `CameraKStateHolder.deviceOrientation` follows the device between start and stop (face up, face down and unknown keep the last value). `selectCamera` is an `os_signpost` interval `CameraK.lensSwitch`, with a `CameraK.lensSwitch.failed` marker for a switch that fails.
- **Desktop cameras are enumerated and selectable**: every camera is listed without opening any, with `LensInfo.id` the `/dev/v4l/by-id` link name (else the node path) on Linux, the `AVCaptureDevice` `uniqueID` on macOS and the DirectShow name on Windows; `""` only for the one default entry offered when the list cannot be read. On Windows cameras open through FFmpeg's DirectShow input (was videoInput). `selectCamera(lens)` takes the first camera of that facing, external cameras included, else the first camera; `selectCamera(id)` opens that camera and returns at its first frame, an id not listed (or a camera gone at open) is `NoCamera`, and a camera that fails to open returns its error and reopens the previous one. A camera that opens but delivers no frame within the first-frame timeout is closed, the previous one reopens, and the switch returns `Timeout(LENS)`, or `Timeout(DEVICE_TYPE)` when only the type changed. On Windows a camera unplugged after it was listed is `NoCamera` at open. The camera lock is per device, so two cameras can run at once. A `DesktopGrabberFactory` receives the selected camera's id on every open, and the grabber it returns is started as returned, so an FFmpeg grabber for a stream is no longer opened as an AVFoundation camera on macOS. Flash and torch `OFF` and zoom 1 succeed while open and any other value is `Unsupported`.

- **Android previews render through CameraX's `CameraXViewfinder`** (`androidx.camera:camera-compose`, at the CameraX version, now a dependency of camerak on Android), not a `PreviewView` in an `AndroidView`: `CameraPreview(holder)`. The frame is fitted to the box (`ContentScale.Fit`, as 1.x's `FIT_CENTER`), and CameraX still picks the implementation mode per device. The overlay spans the preview's whole box, letterbox bars included, as it did over the `PreviewView`.
- **A plugin is attached with its own `CameraKPluginContext`**: each attachment gets a new context whose `scope` is a supervisor child of the holder's scope, cancelled right after `onDetach`. A throw from `onAttach`, `onDetach` or a coroutine in that scope, a `reportFailure`, or a frame registration through `context.frames` that comes back rejected sets that attachment's `failure` and emits one `CameraKEvent.PluginFailed` with the plugin's `id`; later failures of the same attachment are only logged, and the camera and the other plugins carry on. `onAttach(context)` is abstract: a plugin implements it.
- **A holder created with a plugin that needs frames binds frame analysis at start**: `CameraKPlugin.needsFrames` defaults to true, and a plugin passed when the holder is created with it set turns on `CameraConfiguration.frameAnalysis` for the engine, so the first analyzer registration needs no rebind. A plugin that reads no frames overrides `needsFrames = false`, as `MediaSaverPlugin` does.
- **`LensInfo`'s constructor requires the `@CameraKEngineApi` opt-in**, as `CameraCapabilities`' does: apps read lenses from `capabilities`, and fakes and alternative engines opt in. `@CameraKEngineApi` has runtime retention.
- **`AspectRatio.previewAspectRatio` requires the `@InternalCameraKApi` opt-in**: it is the preview's own sizing helper, public for the first-party modules only.
### Changed
- **`focusAt` on Android returns `Success` when autofocus ends without locking**, as iOS does once focus stops adjusting: CameraX reports the tap unsuccessful both when AF ends unlocked and when its 5 s deadline passes mid-search, and `focusAt` returned `Timeout(FOCUS_POINT)` for both, so on the Galaxy S23 in the dark every tap failed after about 630 ms though focus had settled. The autofocus state of a frame after CameraX answers now tells them apart: AF that ended is `Success`, AF still searching is `Timeout(FOCUS_POINT)`.
- **The OCR plugin works with ML Kit's unbundled model**: `camerak-ocr` still depends on the bundled `com.google.mlkit:text-recognition`; an Android app that excludes it and adds `com.google.android.gms:play-services-mlkit-text-recognition`, which has the same API, gets the model from Play services on first use. Until it is downloaded `recognize` returns `Failure(Internal)` with ML Kit's exception as its cause, and live frames produce no results. The plugins guide's OCR section shows the swap.
- **The platform engines are split by responsibility** (internal): `AndroidCameraEngine` delegates to its session, lens catalogue, controls and recording binding, and the iOS `AppleCameraEngine` and `CustomCameraController` to their session lifecycle and queue, inputs, still capture, controls, rotation and capabilities. No file is over 600 lines, which the build checks. Behaviour and the public API do not change.

- **`@CameraKEngineApi`** (opt-in required, error level) on the engine SPI and the constructors of library-built value types, for fakes and alternative backends, with no ABI promise; and **`@CameraKPlatformApi`** (warning level) on declarations that expose a platform SDK type.
- **The engine SPI** (`com.kashif.cameraK.engine`, behind `@CameraKEngineApi`): `CameraEngine`, whose KDoc states the ten rules every engine follows, `CameraEngineFactory`, `EngineState`, `EngineRecordingEvent`, `HardwareState`, `DesiredHardware`, `CameraSelection`, `PlatformPreviewSource` (with `PreviewAttachment` on Android and `PreviewFrame` on desktop) and `CameraKEnvironment`, which carries the dispatchers, the time source, the parent job and the permission checker an engine runs under. `CameraKStateHolder` runs on them, through a `CameraKStateHolder(config, engineFactory, plugins, environment)` constructor behind the same opt-in, and each platform has an engine (CameraX, AVFoundation, JavaCV). Rule 5: `hardware` and `zoom` change only from what the platform reports, never from the requested value; flash on Android and iOS, which has no platform observer, is a read-back of the platform object (`ImageCapture.flashMode`; on iOS the mode validated against `photoOutput.supportedFlashModes`), published before `setFlashMode` returns, which returns it. `CameraKStateHolder.previewSource` returns the engine's `PlatformPreviewSource` for camerak's preview; it is also behind `@InternalCameraKApi`, public only because camerak is another module.
- **The frame analysis API** (`com.kashif.cameraK.frames`): `FrameSource`, `FrameAnalyzer`, `FrameRegistration`, `FrameSpec`, `CameraFrame`, `FramePlane` (with a ranged `copyTo(destination, destinationOffset, sourceOffset, length)`), `RetainedFrame` and `FrameRect`, and `CameraFrame.copyLuma(destination, destinationOffset = 0, scratch = null)`, which copies the luma plane without row padding from YUV_420 frames and computes BT.601 luma from RGBA_8888 frames; pass a `scratch` of at least `width * 4` bytes to keep RGBA copies allocation-free. A registration whose session format is not in `FrameSpec.acceptedFormats` is rejected through `FrameRegistration.rejection` instead of receiving frames. The Android, iOS and desktop engines deliver frames through it. A non-fatal throwable from an analyzer is logged and the next frame is delivered; a fatal one, such as `OutOfMemoryError`, propagates. Each `RetainedFrame` releases once: closing it again does nothing.
- **`camerak-testing` fakes**, for apps' test source sets: `FakeCameraEngine`, a scripted engine that passes the same contract kit as the real engines, with `calls` listing every engine call and a scripting surface that needs no opt-in; `FakeCapabilities` and `FakeCaptures` for its inputs; `FakeFrameSource`, which activates a registration whose `acceptedFormats` holds the session format, rejects any other with `Unsupported(ANALYSIS_FORMAT)`, and through `emit(frame)` delivers to every active registration while the engine is open, admitting each frame through the same gate as the real sources: a frame inside a registration's `maxFps` interval, by its `timestampNanos`, or one that arrives while that registration's analyzer is busy, is skipped for it, and an admitted frame arrives as the same object (`maxRetained` is the real sources' job and is not enforced); `TestFrame.luma(...)` and `TestFrame.rgba(...)`, YUV_420 and RGBA_8888 frames over bytes the test gives; `fakeCameraKStateHolder(fake)`, a holder over a `FakeCameraEngine` that needs no opt-in; `FakePermissionChecker`, granted by default with a status settable per permission; and `TestScope.cameraKTestEnvironment()`, which puts every CameraK dispatcher and the clock on the test scheduler. `FakeCameraEngine.setZoom` clamps into the camera's range as the engines do, and `FakeFrameSource.emit` logs an analyzer's non-fatal throwable, a failed assertion included, and goes on, so a test asserts on what its analyzer recorded after `emit` returns.
- **`rememberCameraKStateHolder(config, plugins, lifecycleOwner)`** (camerak): remembers a `CameraKStateHolder` over the platform's camera, starts and stops it with `lifecycleOwner` (pass null to drive it yourself) and re-checks the permission on resume. The holder lives in the nearest `ViewModelStoreOwner`, so an Activity recreation such as a rotation keeps the same holder and any live recording, and it closes when that owner is cleared; with no owner it closes on dispose. A new configuration closes the old holder, and the new one opens the camera only once the old one has closed, waiting at most 10 s before it logs a warning and opens anyway. The lens, camera device type, flash, torch and zoom the user chose are saved with `rememberSaveable` and restored after process death; the zoom through `initialZoomRatio`. While the holder is on the platform default camera no lens is saved, so a configuration with no lens stays the platform default. camerak depends on `org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose` 2.9.6 for it.
- **`camerak-core` exports `org.jetbrains.androidx.lifecycle:lifecycle-runtime`** 2.9.6 (`api`, every platform), whose `Lifecycle` `bindToLifecycle` takes. On Android it resolves `androidx.lifecycle:lifecycle-runtime` 2.9.4, which the core previously reached only through `activity-compose` before the module split.
- **`CameraKStateHolder.bindToLifecycle(lifecycle): AutoCloseable`** (`com.kashif.cameraK.lifecycle`), for a holder the app keeps in its own ViewModel: the holder starts when the lifecycle reaches STARTED, stops below it, and re-checks the permission on every move to RESUMED. Closing the binding stops the holder without closing it.
- **`rememberRecordingElapsed(holder, tick = 1.seconds): State<Duration>`** (camerak): the live recording's elapsed time, updated once per `tick` while recording, held while paused, and zero otherwise.
- **`cycleFlashMode()`, `toggleTorch()` and `toggleLens()`** (`com.kashif.cameraK.controls`), suspend extensions on `CameraKStateHolder`: the next flash mode in `OFF`, `AUTO`, `ON` that the current camera offers, the torch `ON` or `OFF`, and the front or back camera.
- **`rememberCameraKPermissionState(vararg permissions, onResult)`** (camerak): a `CameraKPermissionState` whose `statuses` are read from the same platform rule as the holder's permission check, again on every resume and after a request, with `allGranted` and `launchRequest()`, which prompts for what can still be asked and reports on the main thread. Nothing is asked on composition. On Android a permanent denial is inferred only after an earlier request; on macOS the camera and the microphone read AVFoundation's `AVMediaTypeVideo` and `AVMediaTypeAudio` authorization. Below iOS 14 the gallery reads as not determined and is never requested: the save raises the add-only prompt.
- **`CameraKScreen(holder, modifier, loading, error, content)`** and **`CameraPreview(holder, modifier, contentDescription, tapToFocus, focusIndicator, overlay)`** (camerak), over the holder's engine preview. The screen shows `loading` while Idle or Starting, the preview with `content` over it while Ready or Interrupted, `error(error, retry)` on Error (retry calls `holder.retry()`) and nothing once Closed. The default slots draw nothing; the default error slot retries a retryable error once until the camera is Ready again and leaves `Permission` to the resume re-check. The desktop preview stops reading frames from a source it no longer shows. On every platform the overlay is laid out over the preview's content rectangle, the largest centred box of the image's aspect ratio (the configured ratio on Android and iOS, the frame's on desktop), with the letterbox bars outside it, so overlay coordinates map 1:1 to the camera image; `CameraPreviewScope.contentBounds` is that rectangle in the overlay's coordinates.
- **Focus and exposure** (`docs/guides/focus-and-exposure.md`): `CameraKStateHolder.focusAt(point: NormalizedPoint)`, `setExposureCompensation(index)` and `resetFocusAndExposure()`, each a `CameraKResult<Unit>`. `NormalizedPoint(x, y)` (`com.kashif.cameraK.controls`) is in [0, 1] over the preview's content rectangle; a point outside it is `Failure(InvalidArgument(FOCUS_POINT))`, and an index outside the bound camera's range `Failure(InvalidArgument(EXPOSURE_COMPENSATION))`, through the new `CameraKError.InvalidArgument(operation)`. `CameraCapabilities` reports per camera `supportsFocusPoint(cameraId)`, `exposureCompensationRange(cameraId)` and `exposureCompensationStep(cameraId)`; `CameraFeature` and `CameraOperation` gain `FOCUS_POINT` and `EXPOSURE_COMPENSATION`; `CameraUIState.exposureCompensationIndex` reports the applied index, `CameraConfiguration.initialExposureCompensationIndex` seeds it, and the holder re-applies it after every bind, switch and restart. `CameraPreview(holder, tapToFocus = true)` focuses where a tap lands in the content rectangle and draws `focusIndicator` (a `FocusTap` with the position, the point and a `FocusOutcome`) until 1.5 s after the answer; with a camera that does not report a focus point a tap does nothing. `CameraKScreen(holder, modifier, tapToFocus, focusIndicator, loading, error, content)` passes `tapToFocus` and `focusIndicator` (default `DefaultFocusIndicator`) to its preview. The engine SPI's `focusAt`, `setExposureCompensation` and `resetFocusAndExposure` default to `Unsupported`, and `FakeCameraEngine` scripts them (`lastFocusPoint`, `failNextFocus`, `reportExposureIndex`). Desktop returns `Unsupported`.
- **Focus and exposure work on Android**: `focusAt` meters at the tapped point of the preview's content rectangle, mapped through the preview's crop, rotation and mirror into the camera's buffer, and answers `Success` when CameraX reports focus, `Timeout(FOCUS_POINT)` when autofocus does not lock, `Busy(FOCUS_POINT)` when a newer tap, a reset or a rebind supersedes it, `Closed` when the camera stops or closes first, even if a start follows at once, and `InvalidState(FOCUS_POINT)` before the preview is attached; metering-only cameras succeed once metering completes. `setExposureCompensation` reports the index CameraX reads back, never the request; a call that a newer call, a reset or a camera switch replaces returns `Busy(EXPOSURE_COMPENSATION)` and leaves the held index as it was, even when the old camera applies it after the switch, and one cut short by a stop returns `Closed`. The index is re-applied, clamped into the new camera's range, after a switch or a restart. `resetFocusAndExposure` cancels metering and returns the index to 0.
- **Focus and exposure work on iOS**: `focusAt` sets the focus and exposure points of interest and answers when the lens settles, `Timeout(FOCUS_POINT)` if it is still adjusting after 2 s; a change of subject area returns the camera to continuous focus and exposure at the centre. iOS has no exposure index, so CameraK defines one: 1/3 EV per step, within the device's target-bias range bounded to ±2 EV (`-6..6` on current iPhones); the published index is the bias the device reports, rounded to a step. CameraK never sets a bias outside the camera's own range: a camera whose bias bound falls just short of a 1/3 EV step does not offer that step, since AVFoundation answers a bias past a bound with an exception Kotlin cannot catch.
- **`CameraPreviewScope.contentBounds`** (camerak): the preview's content rectangle, the area the image fills with the letterbox bars excluded, in the overlay's coordinates. The overlay is laid out over it on every platform.
- **camerak's `compose-stability.conf` lists the 2.0 value types**: `ZoomState`, `RecordingState`, `CameraKError`, `CapturedImage`, `RecordedVideo`, `CameraKResult` and their subtypes.

- **The plugin SPI**: `CameraKPlugin.onAttach(context: CameraKPluginContext)`, `id` and `needsFrames`; in `com.kashif.cameraK.plugin`, `CameraKPluginContext`, which carries the attachment's `scope`, `failure`, `dispatchers`, the holder's `cameraState`, `uiState`, `capabilities`, `deviceOrientation`, `recordingState`, `frames` and `captures`, and `reportFailure(error)`, and no commands; `PluginStatus` (`Idle`, `Running`, `Paused`, `Failed(error)`) for a plugin to publish; and `CameraKPluginContext.launchPerSession(block)`, which runs `block` once per Ready session and cancels it when the camera leaves Ready. The context's `recordingState` stays `Idle` until the holder records.
- **Recording on the holder**: `CameraKStateHolder.recordingState` (Idle, Starting, Recording, Paused, Stopping, then Finished with the outcome) and the suspend commands `prepareRecording(config)`, `startRecording(config)`, `stopRecording()`, `pauseRecording()` and `resumeRecording()`. A start returns once the platform confirms it, `Failure(Busy(RECORD_START))` while one is live, `Failure(Permission(MICROPHONE, status))` with `enableAudio` and no microphone permission, and `Failure(Timeout(RECORD_START))` when the platform does not confirm within 5 s. A stop the platform does not finalize within 5 s returns `Failure(Timeout(RECORD_STOP))` and leaves the recording Finished with reason ERROR. `pauseRecording` and `resumeRecording` return `Failure(NotReady)` while the camera is Interrupted; `stopRecording` still reaches the platform then, so the file is finalized. `stop()` during a recording keeps the camera open, and Ready, for 2 s: a `start()` in that window, such as an Activity recreation's, carries on with the same recording, and otherwise the recording ends as INTERRUPTED and the camera closes. `close()` ends a live recording as SHUTDOWN. Each ending is bounded by 5 s. A plugin's `CameraKPluginContext.recordingState` is the holder's. The Android, iOS and desktop engines record, each enforcing `maxDuration` and `maxFileSizeBytes` and ending the recording as MAX_DURATION or MAX_FILE_SIZE.
- **`CameraKEvent.RecordingEnded(recordingId, result, reason)`**: a recording the app did not stop ended, at a duration or size limit, by an interruption, a platform error, a host stop or `close()`. The same outcome is in `recordingState` as Finished; a stop the app asked for returns its outcome from `stopRecording()` instead.
- **The engine SPI's recording contract** (`CameraEngine.recordingEvents` KDoc): every recording an engine started yields exactly one `Finalized`, whether the app or the platform ended it, in start order, possibly after `stopRecording` returns. The holder matches a late `Finalized` to the recording it belongs to, so it never ends the next one.
- **`CameraKStateHolder.frames`**: the engine's `FrameSource`, for an app's own frame analysis; plugins get the same source from their context. It delivers frames on Android, iOS and desktop.
- **Frame analysis on Android**: one `ImageAnalysis` (keep-only-latest) in `CameraConfiguration.analysisFormat` (YUV_420 or RGBA_8888) and `analysisResolution` (by default CameraX's analysis size, 640x480) under the configured aspect ratio, shared by every registration. Frames carry the rotation, timestamp and crop rect CameraX reports, so a consumer such as a 1D barcode decoder can rotate a portrait frame (#168). A synchronous registration reads the frame on the analysis thread with no copy; other registrations get one pooled copy each frame, on their own worker, within their `maxFps` and `maxRetained`. Without `frameAnalysis` the first registration binds the analysis once, and during a recording only after it ends. `supportedAnalysisFormats` is `{YUV_420, RGBA_8888}`.
- **Frame analysis on iOS**: one `AVCaptureVideoDataOutput` in 420f that drops late frames, attached for the first registration (or at start with `frameAnalysis`) and removed after the last; while a recording runs the outputs do not change, and a registration that needs the output waits, inactive, until the recording ends. A synchronous registration reads the frame on the output's queue; a retained frame holds the sample buffer, at most once per registration and twice in all, and copies the luma beyond that: such a copy is YUV_420 with one plane, the luma, so a consumer checks `planes.size`. iOS does not read `analysisResolution`; analysis frames come at the session's size, which their `width` and `height` state.
- **Frame analysis on desktop**: frames in `CameraConfiguration.analysisFormat`, RGBA_8888 or full-range BT.601 I420 (YUV_420), converted once per frame from the cropped, mirrored frame the preview shows, and only when an analyzer takes it; with no registration nothing is converted. `analysisResolution` scales the centred region of its aspect ratio bilinearly, so nothing is stretched, and null keeps the frame's size. A 0x0 or negative `analysisResolution` logs one warning per session and skips analysis for that session; the preview, stills and recordings carry on. A registration is active at once while the camera is open. A synchronous registration runs on the producer thread and reads the converted frame, since desktop has no platform buffer; every other registration has its own conflated worker, so a busy analyzer misses frames and never queues them. Frames come from a pool sized from the registrations (the sum of their `maxRetained`, one slot each for the preview, a still, the recorder and every analyzer, and two spare), resized when a registration is made or closed, so an analyzer at its `maxRetained` is skipped alone while the preview, stills, the recording and every other analyzer keep getting frames. A closed registration keeps its slots until it releases the frames it retained. A frame that cannot be converted is skipped for analysis and logged. `supportedAnalysisFormats` is `{YUV_420, RGBA_8888}`.
- **`CameraFrame.imageProxy`** (Android) and **`CameraFrame.pixelBuffer`** (iOS), `@CameraKPlatformApi`: the platform frame behind a synchronous registration's frame, and null on any other.
- **Explicit API mode and ABI dumps**: every published module (camerak-core, camerak, camerak-testing and the four plugins) builds in Kotlin's explicit API mode, and its public ABI is recorded in committed dumps (`api/android/*.api`, `api/desktop/*.api`, `api/*.klib.api` for iOS). The build fails on any ABI change the dumps do not record, so each API change is reviewed as a dump diff.
- **Dependency verification** (contributors): `gradle/verification-metadata.xml` pins the sha256 of every dependency the build, the tests and the release resolve, and Gradle enforces it. A dependency update, a Dependabot one included, fails the build until the file is regenerated; CONTRIBUTING.md gives the commands.
- **The 2.0 migration guide** (`docs/migration/2.0.md`), and the README and every page under `docs/` rewritten to the 2.0 API: no page teaches a removed symbol, `docs/api/controller.md` is gone, recording is documented in the core, and every KDoc code sample is a compiled `@sample` function, which the published API docs render; the docs build fails on an unresolved `@sample` or KDoc link. `docs/device-checklist.md` lists the device runs each release candidate passes before release.
- **Backups** (docs): backup stays on, and the configuration guide's Backups section shows how an app keeps CameraK's folder out of it: `NSURLIsExcludedFromBackupKey` and a file protection class on iOS's `Documents/CameraK`, and Auto Backup `data-extraction-rules` and `full-backup-content` excluding `files/CameraK` on Android, and names desktop's folders, which CameraK leaves to the user's backup: captures in `~/Documents/CameraK`, recordings in `~/Movies/CameraK` on macOS and `~/Videos/CameraK` elsewhere. The migration guide's storage section links it.
- **Convention plugins** (contributors): a `build-logic/` included build holds `camerak.kmp-library` (targets, Java 17, explicit API mode, the ABI check, the Android SDK levels, Dokka), `camerak.publish` and `camerak.relocation`, and every published module applies them and keeps only its own dependencies and namespace. The published artifacts, POMs, Gradle module metadata and ABI dumps do not change.
### Deprecated
- **1.x calls that 2.0 replaces are ERROR-level hints**: they no longer compile, their quick fix writes the 2.0 call, and a call compiled against 1.x that reaches one throws `UnsupportedOperationException("Removed in CameraK 2.0; see the migration guide")`. The holder's `captureImage()` (use `capture()`), `toggleFlashMode()` (`cycleFlashMode()`), `toggleTorchMode()` (`toggleTorch()`), `toggleCameraLens()` (`toggleLens()`), `shutdown()` (`close()`) and `getCameraCapabilities()` (`capabilities.value`); `rememberCameraKState` (`rememberCameraKStateHolder(config)`); `CameraKScreen(cameraState = ...)` (`CameraKScreen(holder, modifier)`); `MediaSaverPlugin.getByteArrayFrom(path)` (`readBytes(saved)`); the desktop `CameraGrabber.grabCurrentFrame()` (`holder.capture()`); the types `ImageCaptureResult` and `VideoCaptureResult` (`CameraKResult<CapturedImage>` and `CameraKResult<RecordedVideo>`), which nothing in 2.0 returns; the named-argument `CameraConfiguration(...)` and `VideoConfiguration(...)` factories (see "built with a DSL"); and the saver's old names (see "Plugin packages are lowercase"). `Directory` is ERROR-level with no replacement and remains only as the type of the `CameraConfiguration(...)` hint's `directory` parameter: captures are app-owned files, and `MediaSaverPlugin` publishes to the gallery through `GalleryDestination`. 2.1 deletes every hint.
- **`AspectRatio.RATIO_9_16`** is deprecated at WARNING, with a quick fix to `RATIO_16_9`: it is the 16:9 ratio on every platform, and the device's orientation decides portrait or landscape. 2.0 still compiles code that uses it.
### Fixed
- **`camerak-analyzer`'s javadoc jar had no API docs**: the module applied no Dokka. It now documents the analyzer as the other modules' jars do.
- **The 2.0 artifacts could not be published**: `camerak-core`'s Apple metadata did not compile (the signpost cinterop, declared only for the iOS targets, is now commonized), `camerak`'s common metadata did not compile (`currentCompositeKeyHashCode` is a `CompositeKeyHashCode` in common code), and the OCR and QR plugins' javadoc jars failed in Dokka. `scripts/verify.sh --full` now publishes every artifact and relocation POM to a scratch repository and checks each coordinate.
- **A plugin that threw an `Error` broke the camera**: `onAttach` and `onDetach` caught only `Exception`, so a `NotImplementedError` (a `TODO()` body) or a `LinkageError` from a plugin ended the session and kept the later plugins from attaching, and from `onDetach` stopped the release before the camera closed. Any non-fatal throwable from a plugin is now logged and reported as `CameraKEvent.PluginFailed`, and the camera and the other plugins carry on. The holder's release always ends its scope, even when the engine's close throws.
- **POM licence said MIT**: every published POM declared the MIT licence while `LICENSE` and the README grant Apache 2.0, so licence scanners saw two contradictory licences. The POMs now declare The Apache License, Version 2.0, from one entry in `gradle.properties`, and the build fails if any POM disagrees with `LICENSE`. All releases, including 1.x, are Apache 2.0.
- **POM metadata**: `ocr_plugin` was published under the name `qrScannerPlugin`, and `qr_scanner_plugin` and `ocr_plugin` both described themselves as "Image Saver Plugin for CameraK". Version, group and the shared POM fields now live once in `gradle.properties`, with each module's name, artifact id and description in its own `gradle.properties`.
- **Desktop capture and recording raced the preview for the camera**: `takePictureToFile()` and the recording loop each called `grab()` and the shared frame converter from their own threads while the preview loop did the same. On Windows the grabber is unsynchronised, so this could crash the JVM; elsewhere a photo could be the preview's half-overwritten buffer, and each extra grab took a frame away from the preview (recording roughly halved the preview rate). One grab loop on its own thread now owns the grabber and converter. A capture saves a copy of that loop's next frame, and recording takes its frames from that loop instead of grabbing its own every 33 ms. If the encoder falls behind, the recording skips to the newest frame rather than queueing. If the camera stops while a recording runs (or was never started), the recording now ends instead of waiting for frames: stopping the recording returns the file when a playable file was kept, and a failure when nothing was written instead of reporting success, and a grabber that stops delivering frames ends the session with an error instead of spinning the grab thread.
- **Desktop freed native handles while they were still in use**: stopping the camera released the frame grabber while the grab loop could still be inside `grab()`, `stopSession()` followed by `cleanup()` released it twice, and stopping a recording stopped the encoder while a frame was still being encoded. Stopping desktop OCR freed the Tesseract handle while a scan could still be running in it. Each handle is now released by the coroutine that uses it, once, after its last call returns; Stopping the camera and stopping OCR return without waiting. A stop followed by a start now waits for the previous grab loop to release the camera before opening it again, instead of running two loops on one grabber. A recorder whose `start()` fails is released, and a second recording start while one is live is refused instead of orphaning the first recorder.
- **The Android image saver ignored the DOCUMENTS destination and the folder name** (1.x `Directory.DOCUMENTS` and `customFolderName`): on API 29+ a `DOCUMENTS` save was inserted into `MediaStore.Images`, which accepts only `DCIM/` and `Pictures/`, so every such save failed. It now goes through `MediaStore.Files` and lands in `Documents/<folderName or CameraK>/`. Below API 29 the saver set no file path, so MediaStore put every image directly in `Pictures/` regardless of the destination and folder name; it now writes to `<destination>/<folderName or CameraK>/` like newer versions. The file is created before the MediaStore row, taking the first free name, so neither an existing file nor a concurrent save with the same name is overwritten.
- **`kotlinx-coroutines-test` shipped to consumers, breaking `Dispatchers.Main`** (#165): `cameraK` declared `kotlinx-coroutines-test` as an `api` dependency of `commonMain`, so it landed in the published POM at runtime scope and reached every app that depends on `camerak` — or on any plugin, since each one re-exports the core with `api`. That artifact registers a `TestMainDispatcherFactory` through `ServiceLoader`, which takes over `Dispatchers.Main`; an app that never calls `Dispatchers.setMain()` then dies with *"Dispatchers.Main was accessed when the platform dispatcher was absent and the test dispatcher was unset"*. Reported on Desktop/Windows, but the leak was on every target. The dependency is now test-only. Consumers who were unknowingly relying on it for their own tests must declare it themselves; the `configurations.all { exclude(...) }` workaround is no longer needed.
- **The iOS image saver did not accept plain file paths** (#183): a capture's path may be a plain file-system path as well as a `file://` URL.
- **Crash on Mac Catalyst during QR/barcode setup** (#70): the 1.x scanner assigned a fixed list of 13 metadata object types, but a Mac camera advertises far fewer (sometimes none), and assigning a type not in `availableMetadataObjectTypes` aborts the process (`NSInvalidArgumentException` in `_buildAndRunGraph`). iOS QR scanning now decodes the analysis frames with Vision and CameraK attaches no metadata output. Note: this covers running an iOS app via Mac Catalyst; a native macOS (AppKit) target is not yet provided.
- **The Android `rememberCameraKPermissionState` read its preferences file on the main thread**, in composition, on every resume and in the request's result: the request record is read and written on `Dispatchers.IO`, and until the first read finishes, just after the first resume, a permission that is not granted reads `NotDetermined`. The statuses and `onResult` are still published on the main thread.
- **The Android preview kept the first Activity's `PreviewView`**: 1.x's `CameraPreviewView` held the view it built; `CameraPreview(holder)` builds no view of its own and renders the engine's preview in `CameraXViewfinder`, so a recreated Activity holds nothing of the destroyed one.
- **Android captures were cropped as portrait on landscape-first displays** (#182): the ViewPort took `ROTATION_0` as portrait, so tablets and Chromebooks cropped stills and video to the wrong orientation. The display's natural orientation decides it, and a preview that moves to a panel of the other natural orientation turned a quarter rebinds with that panel's rotation.
- **Android recording worked on the main thread**: the Recorder, the `VideoCapture` and the quality selector are built off the main thread, and only CameraX's bind call runs there; the finished file's playability check reads it on an I/O thread.
- **Android external cameras opened the built-in back camera**: selecting a `LENS_FACING_EXTERNAL` camera by `cameraId` required the back facing before filtering by id, so CameraX dropped the external camera and the selector fell back to the built-in back camera. An external camera is now selected by its id alone. One CameraX does not offer is replaced by the default back camera, with a warning, before anything is unbound; on a device with no back camera either, `start` and `selectCamera` return `CameraKError.NoCamera`, and `selectCamera` leaves the current camera bound. An external camera that disappears while bound (unplugged) is not replaced on a later rebind (a recording's prepare or start, a display rotation): the rebind fails with `NoCamera` and the camera state becomes `Failed(NoCamera)`, rather than switching to the back camera without telling the app.
- **The Sample said "Camera access was denied" before asking** (Sample): a camera permission not asked yet (`NotDetermined`) showed the denial notice, so a fresh desktop run opened with it, and a `Limited` camera hid the preview. `NotDetermined` now shows no notice, `Limited` counts as granted, and only `Denied` reads as a refusal.
- **Android ultra-wide photos came back the wrong shape** (Pixel 7): a device type that maps to a physical lens inside a logical multi-camera (the Pixel 7's ultra-wide, camera 3 inside camera 0) binds the logical camera, and with no target resolution CameraX picked the logical camera's 4032x3024, which the ultra-wide does not output; a 4:3 photo came back 1920x1914 and a 1:1 photo 1410x1914. The preview, the still and the analysis now keep only the sizes that lens outputs for their format, read from its own stream configuration map, so the same photo is 4000x3000. When the sizes cannot be read, the failure is logged and CameraX's choice stands.
- **`focusAt` timed out on the Android ultra-wide** (Pixel 7): CameraX described the pinned lens's logical camera, which focuses, so the action asked for autofocus on a fixed-focus lens, which never locked, and `focusAt` returned `Timeout(FOCUS_POINT)` after 5 s. A pinned lens now meters only what it can itself: no AF on a lens with a minimum focus distance of 0 or no AF region, no AE or AWB where it takes no region of that kind. The fixed-focus ultra-wide meters exposure and returns `Success`; a pinned lens that meters nothing at a point reports no focus point in the capabilities and returns `Unsupported(FOCUS_POINT)`.
- **Exposure compensation was lost after a start on Android** (Galaxy S23): an index sent while CameraX was still configuring the session it binds, as the re-apply after a start or restart is, never reached the camera; every frame after carried 0 while CameraK reported the index, and `setExposureCompensation` sent just after a start never returned. An index now goes out once the session's first capture result shows it streaming, and a command completes on CameraX's answer or on the first frame that carries the index, whichever comes first, rather than waiting for auto-exposure to settle, which took up to 44 frames in a dark room.
- **iOS opened a back camera for a FRONT device type the front lacks**: a FRONT `TELEPHOTO` or `ULTRA_WIDE` request fell back to that type on the back, so an iPhone 14 Pro opened its back telephoto or ultra-wide. As on Android, a type the facing lacks now logs a warning and opens that facing's default camera; with no camera facing the request at all, `FRONT` is `NoCamera` and `BACK` takes a camera of no facing (an external or Mac camera).
- **iOS `pauseRecording` always failed**: AVCaptureMovieFileOutput applies a pause on its own queue, so the engine read the output as still recording and returned `Hardware`, though the file had stopped growing; the recording was never resumed and its file held only the time before the pause. `pauseRecording` and `resumeRecording` now return once the output reports the change (within 1 s), and `RecordedVideo.duration` is the finished file's duration rather than the wall clock less the pauses.
- **iOS sessions kept their camera after close**: closing only stopped the session, which kept its camera input, its outputs and its preview layer's reference until Kotlin/Native's collector freed it. A device run that created and closed hundreds of holders of one camera in one process saw the time to Ready rise from about 320 ms to 5 s, then `Timeout(START)`. Close now removes every input and output and detaches the preview layer from the session.
- **iOS `setTorchMode(OFF)` was `Unsupported(TORCH)` on a camera without a torch**, though the capabilities list `OFF`. `OFF` now always succeeds; the camera is not touched.
- **iOS `QUALITY` captures ignored `targetResolution`**: `QUALITY` opened the photo output to the camera's largest photo, so a 16:9 capture aimed at 1280x720 came out 4224x2376. With a target, `QUALITY` keeps the session preset's size when that reaches the target, and otherwise asks for the smallest photo the camera offers that reaches it. A 4:3 or 1:1 target is still served by the full-sensor photo preset, the only 4:3 preset above 640x480.
- **iOS lost the first capture after `start()` in most sessions** (iPhone 14 Pro, 14 Pro Max): `startRunning` sometimes returns in a few milliseconds, before the camera is really running, and the first capture then failed with -11803 and came back `NotReady`, flash or not. It happened in about two sessions in three on both phones. A capture that fails with -11803 while the session reports running is now issued once more, 0.5 s later, with new settings; a second failure, a cancelled capture, a stopped session, a lens switch or a close in the meantime ends it as before.
- **iOS could freeze while a camera started** (iPhone 14 Pro, iOS 27.3): from iOS 17 the engine made the rotation coordinator on its session queue, and `AVCaptureDevice.RotationCoordinator` waits for the main thread when it is made. With the main thread making a preview layer, which waits on the session, neither moved; every later start timed out and iOS killed the app. The coordinator is now made on the main thread, as in Apple's AVCam.
- **`CameraKScreen`'s default error slot could skip its retry**: it re-armed its one retry when its own state collector saw the camera reach Ready, and a camera that failed again before the next frame was never seen as Ready, so the new error was not retried. The holder now counts each Ready, and a camera that reached Ready since the last retry always earns another.
- **iOS could crash capturing after a lens switch that lost the camera**: when the session refused the new camera and would not take the previous one back, it was left without a camera while the engine kept the previous one, and a capture then raised an exception that ends the app. The engine now forgets the lost camera, and a capture or its retry on a photo output without an active video connection returns `NotReady`.
- **iOS could crash closing a camera off the main thread**: close took the session out of the preview layer on the main thread, which configures the session, while the session queue stopped it; stopping a session inside a configuration raises an exception that ends the app. A close after a recording, or from another thread, could hit it. The session is now stopped only after the preview layer has let go of it.
- **iOS torch could stay dark after `setTorchMode(ON)`** (iPhone 14 Pro): a session whose `startRunning` returns in a few milliseconds starts for real about 0.6 s later, and the system then turns off the torch it was given, so the torch read back OFF. When the device reports the torch turned off without the engine asking, the engine sets the asked-for mode again, once per start, torch command and camera, and only while the session is running, so a torch the system keeps turning off is not fought over and an interrupted session is left alone.
- **Desktop could undercount its frame pool**: a frame analyzer closed while the producer was handing it a frame was dropped from the pool count before the frame was counted, and an analyzer that kept that frame held a slot the pool no longer reserved. The frame is now counted before the analyzer's gate lets it in.
- **Android live OCR could corrupt a frame ML Kit was still reading**: after a recognition timed out, the next frame was written into the array the abandoned ML Kit task could still be reading. A frame after a timeout now gets a new array.
- **Android recorded from the wrong lens on a physical camera** (Pixel 7): a lens CameraK binds as a physical lens of a logical camera, such as the Pixel 7's ultra-wide, has every use case pinned to it, but VideoCapture was built without the pin, so a recording streamed from the logical camera's own lens while the preview showed the ultra-wide. VideoCapture is now pinned to the bound lens, and one prepared on another camera is built again for the new one.
- **Android closed the camera on every rotation without a recording**: the holder stayed in its ViewModel, but the Activity's stop for the configuration change stopped the camera, which reopened in the new Activity, with the state back through Starting. `rememberCameraKStateHolder` no longer stops the holder when the Activity stops only to be recreated; leaving the screen or the app still stops it at once.
- **Android camera enumeration failures were logged without their cause**: listing the cameras and reading a camera's characteristics logged only the exception's message, and reading its physical lenses logged nothing. Each logs the operation and the throwable before using its fallback.

### Sample
- **The Sample is redesigned**: its own design system (`SampleTheme` tokens, Inter and Space Grotesk, and atoms in `org.company.app.designsystem`) and six designed screens: the camera with PHOTO, VIDEO, QR, TEXT and ANALYZE modes, each mode's sheet, the settings sheet (now with Save to gallery) and a permission screen that offers Open Settings only for a permanently denied camera. It shows a focus reticle where you tap and an exposure slider beside it, and returns focus and exposure to the camera's own on a mode or lens switch. The benchmarks find the shutter by its description ("Take photo") and cycle the Sample's three ratios.
- **The iOS Sample builds in Xcode**: the `iosApp` target searches `Sample/build/xcode-frameworks` for the `ComposeApp` framework and links it, and excludes x86_64 from simulator builds, the architecture the libraries no longer build. `xcodebuild -project iosApp/iosApp.xcodeproj -scheme iosApp -destination 'generic/platform=iOS Simulator' -configuration Debug build` succeeds; `docs/device-checklist.md` runs it on each release candidate.
- **The TensorFlow Lite demo is removed**: the object-detection screen, the `kflite` dependency and the TensorFlowLite pods leave the Sample, and with them CocoaPods, so the iOS Sample builds with Xcode and Gradle only (open `iosApp/iosApp.xcodeproj`). The QR, OCR, media saver and analyzer screens remain, and the Android Sample's minSdk is the libraries' 23.
- **The Sample's permissions and SDK levels**: the Android Sample targets SDK 36, its compileSdk; asks for the microphone its recordings use when it opens, `WRITE_EXTERNAL_STORAGE` only up to Android 9 (`maxSdkVersion="28"`) and gallery access only when the media saver auto-saves; and the iOS Sample's microphone prompt has text. It shows a failed gallery save as a notice. It asks once per set of permissions: a rotation no longer asks again for a microphone just refused. On a screen wider than tall, as a phone held sideways, the controls sit beside the preview instead of under it, where they left the preview a strip about 90 pixels tall on a Pixel 7; a change of shape lays the same preview out again, and the shutter row's icons turn only by what the screen has not turned already.
- **The iOS Sample launches on iOS 27**: iOS 27 stops an app with no scene manifest at launch (`EXC_BREAKPOINT` in `_UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`). The `iosApp` host now makes its window in a `SceneDelegate`, named in the Info.plist's scene manifest.
- **The Sample logs through `CameraKLogger`** instead of `println`, keeps only a summary of the analyzer's latest frame instead of its JPEG, and its aspect-ratio button cycles `RATIO_4_3`, `RATIO_16_9` and `RATIO_1_1`.

## [1.1] - 2026-06-30

### Fixed
- **Android photos cropped / reduced field-of-view** (#136): captured stills were zoomed-in vs the preview (e.g. a 4080×3060 sensor saved as a 3060×2295 centre crop). Cause: CameraK always bound a 16:9 `VideoCapture` use case in the photo `UseCaseGroup`, and the shared `ViewPort` had to fit every use case — so the 16:9 video shrank the common field of view for the 4:3 still (StreamSharing masked it only when 4+ use cases were bound). `VideoCapture` is now bound lazily — only while a recording is active — so photos use the full sensor field of view. A lens/device switch or a second `startRecording()` during recording is now rejected (they would tear down or orphan the live session), and a failed recording start rolls back so later photos stay full-FOV. Verified on a Galaxy S23 across photo/record/photo-after-record.
- **Android captured photo aspect ratio & orientation** (#136, follow-up): the 1.0 fix letterboxed the preview but, on real hardware, the **saved photo** still came out wrong — e.g. a portrait `RATIO_4_3` capture saved as a cropped 4:3 *landscape*. Root cause (found via on-device testing): three orientation sources disagreed — the capture rotation/EXIF was driven by the accelerometer while the ViewPort crop and preview followed the **display** rotation. Fixes: (1) the ViewPort `Rational` is now orientation-aware (portrait `RATIO_4_3` → 3:4) and rebuilt on a portrait↔landscape rotation; (2) capture `targetRotation` now follows the display rotation — the same source as the ViewPort and preview — so all three agree (WYSIWYG). Verified on a Galaxy S23 across all four ratios × both orientations × with/without the analyzer plugin (StreamSharing).
- **Android rotation during recording** (#147): a portrait↔landscape flip mid-recording no longer tears down the active recording. The ViewPort rebuild is deferred and applied when the recording finalizes; a recording that finalizes on error also clears its state so later rotations rebind correctly. `setTargetOrientation(null)` now reverts to the display rotation (consistent with auto mode) instead of a possibly-stale sensor orientation.

### Changed (behavior)
- **`targetResolution` no longer overrides `aspectRatio`** (Android): when both are set, the aspect ratio is the primary constraint and the resolution is the preferred size within it. Previously a target like `1920×1080` forced 16:9 output even when `RATIO_4_3` was requested.
- **Capture orientation in display-locked apps** (Android): an activity locked to one orientation now produces photos in that orientation (matching its preview) rather than sensor-rotated stills. Apps wanting sensor-based rotation should leave the activity orientation unlocked or use `setTargetOrientation()`.

## [1.0] - 2026-06-19

### Added
- **Opt-in logging (`CameraKLogger`)** (#133): internal logging is now disabled by default and routed through `CameraKLogger`. Set `CameraKLogger.enabled = true` to turn it on, or provide a custom `CameraKLogger.sink` to forward logs to your own logger.
- **`mirrorFrontCamera` configuration** (#112): optionally mirror front-camera captures to match the mirrored preview. Defaults to `false`. iOS and the Android byte-array path bake the flip into pixels; the Android file path records it as an EXIF orientation tag.
- **CI build check** (#129): a workflow builds all targets on every PR; merges are gated on passing checks and resolved review conversations.

### Changed
- **Better barcode/QR detection** (#130) on Android and iOS (stride-aware luminance, `TRY_HARDER`, inverted retry).
- **Android analyzer** now emits decodable JPEG frames (matching iOS) and runs off the main thread, fixing frame backpressure and `Could not decode ByteArray to Bitmap` consumers.
- **`setPreferredCameraDeviceType()`** now performs a live re-bind instead of requiring reinitialization.

### Removed (breaking)
- Deprecated `CameraController.takePicture()` (returned `ByteArray`) — use `takePictureToFile()`.
- Legacy callback-based `CameraPreview` API and the new/old API toggle.
- Dead `returnFilePath` flag and other removed-API references in docs. See the migration table in the README.

### Fixed
- **Plugin lifecycle leaks**: plugins could not remove what they registered, so listeners/outputs/analyzers accumulated on every camera re-init (lens switch, recompose), and coroutines/outputs leaked past detach. Fixes:
  - **Core**: added `CameraController.removeImageCaptureListener(...)` and iOS `safeRemoveOutput(...)` / `clearMetadataObjectsDelegate()`; `pluginScope` is now a StateHolder-owned child scope that `shutdown()` actually cancels (the old doc claimed this but never did); `attachedPlugins` access is synchronized and ignores duplicate attaches; `getReadyCameraController()` returns null on camera error instead of hanging forever.
  - **ImageSaverPlugin**: no longer double-saves after a re-attach (single listener, re-registered per Ready, removed on detach; saves run on `pluginScope`).
  - **AnalyzerPlugin / QRScannerPlugin / OcrPlugin**: each setup now returns a teardown handle; the plugin removes the prior analyzer/output before re-registering on a new Ready and on detach (Android `unregisterImageAnalyzer`, iOS `safeRemoveOutput` / cleared delegate, desktop cancels the collector scope) instead of stacking one per Ready. Frame/result flows are buffered (`DROP_OLDEST`) instead of spawning a coroutine per frame; `OcrPlugin.ocrFlow` is now a buffered channel that isn't closed on detach (so re-attach works) and OCR releases its ML Kit / Tesseract resources.
  - **VideoRecorderPlugin**: `startRecording()` while already recording is rejected instead of orphaning the timer/recorder; `shutdown()` now detaches plugins before resetting recording state so an in-flight recording is stopped (and emits `RecordingStopped`) before teardown; Android `stopRecording()` no longer hangs forever if the finalize event never arrives (5s timeout). iOS pause/resume and desktop pause limitations are now documented in code.
  - **Desktop `saveImage`**: writes to a real per-user directory (`~/Pictures` / `~/Documents`, honoring `customFolderName`) and respects `imageFormat`, instead of a relative dir literally named `PICTURES`; failures are logged and reported instead of silently swallowed.
- **iOS underexposed/black photos** (#138): `MemoryManager` compared `physicalMemory` to itself, so it reported 100% usage and `isUnderMemoryPressure()` latched on permanently. That made every capture downshift the session preset (`adjustSessionQuality`) synchronously right before `capturePhotoWithSettings`, capturing the still mid-reconfiguration before auto-exposure re-converged. Most visible on front-camera selfies; masked when a plugin (OCR/QR/Analyzer) kept an `AVCaptureVideoDataOutput` streaming. Memory pressure is now driven by the system memory-warning notification, and the capture no longer reconfigures the preset at shot time.
- **Android aspect ratio mismatch** (#136): a configured ratio (e.g. `RATIO_4_3`) no longer produces a photo that's a crop of the full-screen (≈16:9) field of view. The preview is now letterboxed to the configured ratio (`FIT_CENTER`) so its shared CameraX `ViewPort` matches the capture — preview FOV equals captured FOV. Adds `CameraController.getAspectRatio()`.
- **iOS preview/capture mismatch on flat devices** (#115, #109): preview no longer distorts when the device is face-up.
- **iOS crash from deprecated video stabilization API** (#113).
- **Android auto-save after capture**: capture listeners are now fired on `takePictureToFile()`.
- **Cross-analyzer buffer corruption**: the shared `ImageProxy` Y-plane buffer is duplicated before reads so concurrent analyzers aren't affected.
- **Desktop `takePictureToFile()`** now writes a real file instead of returning an empty path.
- **`ImageSaverPlugin.getByteArrayFrom()`** (Android) now reads raw file paths before falling back to `ContentResolver`.
- **Plugin initialization timing** (#52): null checks and graceful failure when the camera isn't ready yet.
- **Desktop Tesseract path resolution** (#51): dynamic tessdata lookup with graceful degradation.
- **Desktop QR scanner** (#50): fixed malformed decode-hints `EnumMap` initialization.
- **iOS image orientation** (#44): captures save in the correct orientation across portrait, landscape, and upside-down.
